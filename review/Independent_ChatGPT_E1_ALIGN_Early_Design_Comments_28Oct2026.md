## Replies to section 4

**Q1 — generic encoder and length-prefixed tuple, but not E_1 tie function:** Support, conditionally. `canonical_bytes` and the length32 framing function belong in shared code **if their implementations and declared input/domain behaviour are genuinely method-agnostic**. Retain the E_1-specific digest, rank and tie implementations inside E_1: a project-wide *tie rule* does not make an implementation that hard-codes E_1 identities into a reusable library. Keep the exact output bytes and old E_1-facing function symbols through explicit imports/aliases; exercise old import callers, the reader's `e1_view_digest`, and the frozen goldens. Confirm no shared module imports E_1 or `source_data` in a newly permitted way. A common encoding utility should not add future method functionality to this package.

**Q2 — guard test versus immediate merge of three encoders:** Prefer **guard test now**. Merging the standalone and coordinator encoders expands the risk and touches protected coordinator code without corresponding E1-ALIGN benefit. Compare canonical bytes for representative valid objects (ASCII and non-ASCII, nested dictionaries/lists, key ordering, separators, integer/length boundaries, and relevant unusual Unicode), and confirm invalid-input behaviour where the contracts demand rejection. Be careful not to infer universal equivalence from a finite corpus; use the applicable canonicalisation contract as the oracle. The guard is a regression alarm, not licence to change any of the three historical encodings. Do not edit the coordinator or its protected functions as part of this package.

**Q3 — `e1_` prefixes inside `E_001/`:** Keep them. They identify E_1-specific responsibilities, avoid gratuitous second renaming immediately after NAMES-1, and do not violate the stable-filename policy (no revision suffix). Ensure imports and fresh-process origin tests reflect the new package location; retain the flat entry file for the Option A wrapper.

**Q4 — preserve E_1 revision 1 under E2R-R14A:** **Only with an explicit, narrowly scoped owner-ratified exception.** E2R-R14A otherwise requires a new revision when an approved implementation, including behaviourally relevant shared helpers, changes. Its present explicit structural exception names NAMES-1 **only**. E1-ALIGN is a separate package, so the NAMES-1 exception does not automatically extend to it. The owner has accepted E1-ALIGN and E_1 revision 1 *in principle*; the eventual E1-ALIGN specification/ratification should explicitly document its own structural-only exception and stringent exact-change/equivalence conditions. A package that does more than authorised moves/import relocation/re-export plus approved non-behavioural test updates cannot claim that exception. Golden equality is necessary but not enough: require the exact transformed source/function-body comparison, import-origin and module-graph proof, reader/view and prefix-isolation cases, security/firewall mutations, Windows full-suite evidence, and no new capability/gate activation. If a behaviourally relevant implementation changes, issue a successor revision instead, or return to the owner for an express reconsideration.

## Additional early cautions for the future specification

1. **Do not accidentally activate the E2R admission system early.** E2R-R57/R58 establish the active SUPPORTED-registry and no-development-flag gate for the separately authorised E_2-readiness implementation. E1-ALIGN may create the folder/layout needed for it, but must not silently introduce or relax runtime admission, owner authorisation, result consumption, or other safety gates. Clarify which enforcement exists already and what is deferred to E2R implementation. No E_1 flag is appropriate only as a layout decision, not as independent permission to execute.
2. **Keep E_1's firewall exemption explicit and narrow.** Extending an exemption to every present/future file inside `E_001/` may conceal an inadvertent new privileged path. List the existing allowable legacy E_1 import/data references and reject new unauthorised ones; test both E_1 legacy allowances and non-E_1 folder rejection (and a same-folder unauthorised probe, where appropriate). A frozen E_1 view-schema payload may remain in the reader, but the reader must not import method code.
3. **Package boundaries and proof:** NAMES-1 first; then separately scoped E1-ALIGN design and code reviews; then the E_2-readiness code. E1-ALIGN moves/imports are HIGH tier, touch the shared reader and demand RECHECK. Protect E_1's six-index/prefix/view/T-05/golden tests, full owner Windows suite, original process safety and coordinator protected ASTs. Document deliberate mapping of old source imports to new locations and any file/name-sensitive assertions, without adding runtime code hashes, archive commit IDs, or Git-history dependence.
