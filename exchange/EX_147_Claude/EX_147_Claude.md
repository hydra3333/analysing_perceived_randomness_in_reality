## 2. The Mode H study as built, and the interpretations the reviewer should check

The sequence a game goes through, all on value-free records, each step refusing on any difference from the frozen study:

1. `manifest` (before the opening record; the ledger's last row must end at `holdout_first - 1`) writes `results/real/holdout/<GAME>/MODE_H_STUDY_MANIFEST_V1.json` (create-only) and a `MODE_H_STUDY_MANIFEST` search-log row.
2. `open` (the fixed sentence typed exactly; the ledger still at `v_f`) writes `source_data/HOLDOUT_OPENED_<GAME>.json` with the two freeze fields and a `HOLDOUT_OPENED` row. The updater v0.2 reads this record with its own checks and the test shows the two readers agree.
3. The first update (the owner's updater): admitted only as an UPDATE reaching `holdout_last`, as `v_a = v_f + 1` (section 3).
4. `Method_Walk_Forward.py plan --mode H --game G`: `_study` (opening record and manifest present, agreeing on `v_f`; the advance record if any; the verified ledger; `admitted_version`), `_check_frozen` (closure and environment equal to the manifest's; the ledger's last row is the admitted version and ends at or after `holdout_last`), no earlier plan, no advance before the plan, the adapter-checked cohort equal to the manifest's cohort; the plan is frozen at `v_a` with the manifest's cohort and targets, the batch-id record names it, one `MODE_H_BATCH` row.
5. `run`: `mode_h_checks` (all of the above again, plus the plan tied to the opening record's manifest and no lifecycle marker) before any run; an OPEN ticket before each run naming the request digest, a DONE ticket after each CONTINUE-class run; an interrupted run's open ticket is closed `FAILED_TO_START` by the next invocation (its run id never reused) and the pair runs again; `BATCH_COMPLETE` (with `pairs`) when every planned pair has its DONE ticket. Every request carries the Mode H binding and the admitted pin; the dispatch gate's slice 1 rules apply (`BATCH_CLOSED` after any marker, `PAIR_ALREADY_DONE`, `NO_OPEN_TICKET`, the pin rules).
6. `score`: refuses without `BATCH_COMPLETE`, after the seal, on a roster that is not every planned pair with exactly one DONE ticket proved by its run folder, or on registered families that differ from the manifest's. A new attempt writes the `MODE_H_REPORT` search-log row, the scoring plan (with the roster digest) and `SCORING_STARTED` (attempt id, roster digest, plan digest) **before** the one outcome read; the outcome reader serves the ten holdout targets only while `BATCH_COMPLETE` and `SCORING_STARTED` exist, `SCORE_COMPLETE` does not, the target is the plan's and `SCORING_STARTED`'s roster digest equals the roster recomputed from the records (`outcome_release_allowed`; design 5.3); the score ledger `mode_h_score_ledger.jsonl` is written create-only in one step; `SCORE_COMPLETE` (ledger digest); the report is built from the accepted ledger lines, never from a second read; an existing report must equal the rebuilt bytes; `MODE_H_SEALED` (ledger and report digests). A rerun resumes the same attempt at whichever point it stopped.
7. `declare-developed` after the seal (GOAL-1).
