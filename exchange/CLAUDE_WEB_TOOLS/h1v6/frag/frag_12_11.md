### 12.11 The production deployment work (new in v6)

- **Read first:** section 0B item 12; the decision log, entries 92 to 98 (the owner's words); `exchange/EX_243_Claude.md` (the record for the reviewer: decisions D1 to D12, the verified facts, and what is NOT decided); any reply of the reviewer to it; OFF-1 in `doc/Direction_for_operational_procedures_v0_3r1.md` section 9; design Appendix J (the install procedure that is to be replaced) and design sections 4.3, 6.1 and 7; `src/package_tools/install_records.py` and `process_check.py`; the MHUP-A package tools under `exchange/CLAUDE_WEB_TOOLS/mhupa/` (the copy tool, the verifier, the suite runner: most of the safety logic to reuse is there).
- **What the owner wants, in his terms:** easy deployment from the development clone to production; re-runnable; clean code and processes built once; backups he can open in Windows; rollback by restoring a backup. Keep it small: one tool, the standard library, no service, no scheduler, no incremental backup chain (the working principle).
- **The design note must settle, with alternatives and a recommendation for each:** (1) the layout of the production folder (which folders it holds; the marker file and what it records, the backup folder among it); (2) what "the release" is and how the tool proves production's code equals it (Claude proposed: a named commit of `main` in the development clone, compared by file hashes); (3) `init` (copying the existing tree with every file hash-checked, the fresh `.venv`, the first snapshot) and `update` (the install check, the locks U and P, the copy, the verification, the install and release records, and when the release time is taken); (4) which safety properties of Appendix J are kept and which are consciously replaced, each one named: nothing terminated; no roster change under an unfinished set; the restore rule; the release record's meaning; (5) `export`: how records return to the development clone, one way, verified, so that both AIs keep reading real results from GitHub and a pre-draw witness push stays possible; (6) the snapshot: which jobs, where its code lives, the "snapshot due" file, verification, what a failed snapshot does to the job's exit status (the live path comes first, as for the league table); (7) restore: never over the broken folder, a restore record, and what a restore means for forward evidence and for OV-1 made after the snapshot; (8) the marker guard: which commands refuse outside production; (9) the edits to passed code (the two launchers, the two sequencers, `process_check.py`, `install_records.py`) and the tests of each mode (a fault after every step, then the same command again, as slice 3 tested the publication); (10) what T017 rehearses; (11) the amendments to ratified documents.
- **To check on the owner's PC, not assume:** File Explorer opening a ZIP64 archive of more than 65,535 entries; the time a snapshot of about 81,500 files takes (Claude's unmeasured estimate: about 100 MB and one to three minutes); that G: and T: are NTFS and on different physical drives.
- **Do not:** propose installing or deploying anything before the deployment layer is reviewed; start the design during the takeover; put Git, or a tool that needs Git, in production; build per-case deploy tools.
