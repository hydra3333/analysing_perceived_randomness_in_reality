## 3. Project in one paragraph

Two games, never pooled, one game per run. **Powerball:** current format since Draw 1144, 19 April 2018; 7 distinct main numbers from 1-35 plus 1 Powerball from 1-20. **Oz Lotto:** current era since Draw 1474, 17 May 2022; 7 from 1-47 and no Powerball barrel; its 3 supplementaries never enter any method view, fit, seed, digest or prediction, and **the evaluator alone** may read a target's supplementaries, after the target is opened and its forecast frozen, solely to classify prize divisions (R2 v0.5 section 2.5). The project builds a Python research system on Windows 11 (the venv is Python 3.15.2) that tests whether past draws hold any predictive structure, using 62 permanently registered methods, E_1-E_62 (room up to E_106; E_63 and later are not registered). Each method produces full rankings and publishes TOP and WORST predictions side by side. Real weekly forecasting (**the prospective mode**, the owner's weekly session MH-1) starts once the owner declares the pipeline **developed** for the released cohort (GOAL-1); later waves keep adding methods afterwards. Its design is ratified (MHUP-R, 3 November 2026; current edition `doc/Predictive_Randomness_ModeH_Update_Prospective_Design_v0_1r7.md`): one command per game runs a small sequencer that alternates a forecasting program and a scoring program one target at a time (forecast N from the draws before it, reveal N, score N, then N+1), then freezes the next draw's forecast before its deadline. The weekly session **is** R3's FINAL_NEXT_DRAW protocol as amended by the design, and the owner's GOAL-1 declaration is R3's "explicit FINAL opening" (design 6.7); its code is the second package, MHUP-B, not yet designed in detail. Before that comes **Mode H**, a precommitted holdout evaluation of every released variant (40 per game, a fixed cohort) on the ten holdout draws per game, each forecast from the draws before it, scored once (design section 5). Its code is the first package, **MHUP-A, installed on 13 November 2026**; by the owner's decision of 13 November 2026 Mode H runs first, game by game, and MHUP-B comes after both games are sealed. At this edition no holdout is opened and no Mode H step has run. Method rankings (league tables) are reports per R3 section 17; they never feed forecasts.

### 5.2 Scientific contract

- **Strict N-1:** target N sees only eligible draws with `draw_number < N`. **T-05:** change N and every later row; every method-visible field, array byte, schema, digest and capability must be identical, and the forecast byte-identical. Orchestration-side provenance may differ; provenance handed to a method must not.

- **Seeds and content identity** come from the permitted training-view digest, never the whole-file hash.
- **Views:** `UNORDERED_SET`, `OPERATOR_DRAWN_ORDER`, `PAIRED_DIAGNOSTIC`; caller-declared; paired views never double-count. New schemas bind `game_id`, era and profile version (the legacy `E1_REAL_U_TRAINING_VIEW_V1` alone is exempt). Dates are opt-in with their own schema and digest.

## 6. Verified technical facts (reuse rather than re-derive)

- The Windows venv `python.exe` is a redirector (CPython `PC/venvlauncher.c`): `Popen.pid` is not the interpreter's PID.
- Windows does not kill children when the parent dies; `TerminateProcess` is asynchronous.
- A `.bat` launched via `Popen` runs under `cmd.exe` with CMD argument parsing (gh-114539): hence `SAFE_ARG` and `%*`.
- The `Run_Experiment.bat` process tree is root `cmd.exe`, a pipe child `cmd.exe` plus `findstr.exe`, a pre-check redirector plus interpreter, then the experiment's redirector plus interpreter. The allow-list is `cmd.exe`, `findstr.exe`, `python.exe`.
- psutil 7.2.2: `children(recursive=True)` filters by creation time against the root only (hence the per-edge check); `kill()`/`terminate()` check PID reuse; `Process.wait()` on Windows has no reuse check.
- `O_NOFOLLOW` does not exist on Windows; symlink refusal there relies on `is_symlink()`. NTFS hard links: the reader's `st_nlink != 1` refusal passes on the owner's drive. The owner's account cannot create symlinks (WinError 1314), so **four** symlink tests skip on Windows (reader contracts, exit receipt, CODE-2's dangling-symlink test, and WF-1B's symlinked-master test); the suite runner allows exactly those modules. A test that creates a symlink without catching `OSError` fails there (T013); hard links work and are the portable way to test the link guard.
- Line endings: Git stores `.md` and `.py` as LF; `.bat` is `text eol=crlf`; `source_data/**` is `-text`. `git archive` applies the `.bat` rule, so hash `.bat` files from `git show`.
- **Python 3.15 makes UTF-8 the default text encoding (PEP 686).** No effect on the project's tests so far.
- **The scorer's figures are byte-identical on Windows and Linux:** `tests/test_wf1b_crossplatform.py` pins a report digest and passed on the owner's Windows (T013, T014, the WF-1B install).
- **Record files and line endings:** Git stores `results/` files as text, so on the owner's `core.autocrlf=true` checkout any Git operation that rewrites one (a rebase, a checkout) gives it CRLF bytes, and a create-only record whose bytes are checked then refuses. The first Powerball report refused this way: both committed Powerball batch records (`plan.json` and the segment record) were `w/crlf` (`git ls-files --eol`), the plan 12,029 bytes against 12,028 in Git. The owner restored them (delete the files, then `git -c core.autocrlf=false checkout -- <batch folder>`), and the report then ran. Reminder R-011 adds a `results/** -text` rule.
- **Exact arithmetic can be slow at full size:** WF-1B's exact Clopper-Pearson bisection over 10,000-trial binomial tails took over an hour per report until PERF-1. Profile at full size on invented data before trusting a run-time estimate.
- **The results updater v0.2** (`src/results_master_v0_2.py`, installed with MHUP-A; checked for the readiness sheet): `BrowserFetcher` (line 666) starts Chrome headless (or Firefox with `--browser firefox`) through Selenium with `SE_AVOID_STATS` and `SE_AVOID_BROWSER_DOWNLOAD` set; `fetch` (line 681) refuses a window reaching the quarantine while the game is closed, stops on a title naming a block or challenge page, checks the final URL with `check_final_url` (line 655: `https` and exactly `www.lotterywest.wa.gov.au`), waits up to 15 s for the expected number of draw headings and parses with `parse_gov` (line 604), which reads each heading's number and date before its numbers and stops on a quarantined draw while the game is closed; `update_game` (line 719) writes the grab create-only, compares the overlap, enforces the first-update admission, writes the backup, replaces the master atomically, appends the ledger row and re-verifies, in that order; `cmd_update` (line 810) refuses before any browser starts when a game is not opened and the date is on or after 1 August 2026, and takes the create-exclusive lock `source_data/.results_master.lock`. ## 8. How to work as primary designer and coder

### 8.1 Workspace

- Work in disposable scratch trees, never on the owner's checkout. Build a tree with `git archive <base>` or a fresh clone, apply your overlay, and run everything there.
- Unpack every received zip into its own fresh directory; keep your scripts elsewhere; run Python that reads untrusted files with `-I`.
- Never let a tool print a quarantined row or the R1 paragraphs that name quarantined draws (their line numbers are in section 5.1). When reading master data for a non-outcome fact, print only the fields needed.
- The cloud sandbox cannot reach lottery sites and must not try.

### 8.2 Design before code (HIGH work)

- Write the design (or the specification change) first and give the reviewer a design-stage review and the chance of a competing design (R-3) before writing code. The owner ratifies any schema or rule change before code depends on it. A speculative candidate built alongside the design is fine (but never during a takeover: section 0, item 4), but it is reviewed only after the design passes unchanged (agreed in EX_038 and applied in E2RC2-RD-03).
- Plan the oracles up front (R-4): invariants, exact-arithmetic checks or independently designed fixtures that give real extra assurance. Proportionate, never decorative.

### 8.3 Your own first tests

- **Mutation checks, within safe limits:** for each safety property, plant a defect in a disposable copy and show a test fails; ship the mutation tool and its output. Never mutate installed files, a live switch, real master or holdout inputs, or live process controls. A test that cannot fail is not evidence.
- For any statistical claim (calibration, exactness, independence), build the smallest exhaustive toy that could break it and enumerate it exactly with `fractions.Fraction`.
- Never "refresh" an expected hash. A mismatch is investigated, not accommodated.

### 8.8 Lessons from Claude's own errors (keep them)

- Check IDs mechanically **and** search for rules without IDs (consolidation: dropped invariants; a miscount).
- State the exact conditions of every "exact" or "calibrated" claim (Sidak instead of Bonferroni; over-broad calibration claims; scored-set selection).
- When the reviewer leans towards suppressing a number, propose labelling instead.
- Scan every script you write for non-ASCII; the file tool can turn `\uXXXX` escapes into literal characters.
- Verifiers: normalise CRLF or use Git's view; give every revision a distinct zip and folder name; read the install log's paths before saying it is safe to commit; commit, check, then push (N1I-C01).
- Any fixture meant to be valid gets its own test proving the reader accepts it; split platform-dependent checks into subtests and skip only what cannot run (TH-1).
- **Static guards must be symbol-aware**, and "nothing else changed" is proved with a frozen exact allowlist of edits, not regex categories (E1-ALIGN).
- **Count before claiming**; compute every hash with a tool and copy it.
- **Shell pitfalls:** `open(p,'wb').write(open(p,'rb').read())` truncates first; an unquoted heredoc expands backticks; `git archive` converts `.bat` to CRLF; never `rm -rf` the shell's own directory.
- **Never let a caller choose safety evidence** (E2RC2-CODE-B01, B02): a parameter "for tests" that points the gate at another orphan marker or registry, or that chooses the execution path, is a bypass. Never accept a caller's boolean that "the gates passed" (E2RC2-B02). Every launch path is under the release rule, including legacy ones (E2RC2-B01).
- **Prove create-only publication**, not "rename won't overwrite" (E2RC2-C01); tell a legitimate empty result from invalid output (C02).
- **Runner tools must match the API they inspect:** T001 stopped because a helper still used CODE-1 v1 attributes. Test task tools against the installed code first.
- **Counts in instructions come from the tools:** a hand-written "the two symlink tests" disagreed with the runner's allowance of three; a hand-written test count was wrong in CODE-1 v1.
- **The suite step before the commit has been skipped twice** (CODE-1 and E_3/E_4 installs; both recorded as departures, both run straight after the push and passed). Say plainly not to skip it, and put the suite command in the same command block as POST, not in a block of its own.
- **Mutation checks find real gaps:** "every variant computed as full memory" passed every E_6 test until a test computed each variant's own setting; a certificate accepting D + 1 alternations passed until a hand case was added. Plan one mutation per variant setting and per verification rule.
- **Do not pin lists other packages will extend** (E_6's test pinned the whole `ADAPTERS` list; the template trial caught it). Assert only your own entry.
- **Compute every worked example in a design note with a tool** (the E_3/E_4 draft had two wrong hand-worked values, caught before sending).
- **An owner decision given before the reviewer's formal reply** is recorded as OWNER-DECIDED, subject to revisiting if the review changes anything (D6-1..D6-5).
- **The owner sometimes saves files into the repository**; a verifier's PRE then stops, or a rebase is blocked. Ask for downloads outside the repository (`E:\TEMP`) and for the reviewer's zips to be uploaded to Claude.
- **Assert the whole of a protected section,** not its heading and points (H1F5-C01: a note placed inside H-1's section 2A passed a builder that checked only part of it).
- **A score's ranking claims need their exact conditions** (W1-C01): the same strictly increasing function of each number's count over the same draws ranks like counting; count-only scores in general need not.
- **Changing a covariate is not ranking-preserving** (W2-B01, a BLOCKER): v0.1 of wave 2 claimed a least-squares slope on harmonic numbers ranks exactly as Method A's logistic slope on ln(age); the reviewer proved the reversal with an exact witness. Prove an equivalence, or search for a witness; never assume one.
- **Every loop that waits for a condition needs a proved exit for every input** (W2R1-C01): an interval narrowing until it excludes zero never does at exactly zero. Test exact zero separately, and add a cap that refuses as an error.
- **Hand-written test expectations go wrong too** (two in wave 2's first helper tests; the code was right). Compute them with a tool.
- **Run Python 3.15 checks in a venv with the project's dependencies;** a bare interpreter fails every module on `numpy` and `psutil` (wave 2, before the evidence run).
- **Never invent a label or status word** that no ratified document defines (WF-1B v1 printed a made-up `BONFERRONI_GUARANTEED...` label; replaced by a boolean and fixed text). Use the vocabulary the specifications give, or ask.
- **Precision bugs hide in conversions:** WF-1B's huge-Fraction-to-decimal conversion lost bits until its numerator was widened (sigma 37.055 instead of 37.047 at p = 1e-300). Test extreme values against an independent route.
- **Canonical encoders already end their bytes with a newline;** adding another gave blank lines in the score ledgers. Records must not hold tuples (only lists). A default argument bound at definition time (`replicates=R`) stopped tests from patching R; use `None`. A function looked up through a module attribute can be patched; one held in a table at import time cannot.
- **Mutation survivors show weak tests:** an early outcome read, a Bonferroni M and a missing Monte Carlo line each survived until a test asserted them. Plan a mutant for each ordering, count and printed figure.
- **Task commands must pass the runner's deny list** (T012: `.bat` text). **Tests must be Windows-safe** (T013: an unguarded `symlink_to`). **Probes must not import package scripts in place** (a `__pycache__` crept into a package; rebuilt). Each cost one rehearsal round.
- **An exact method can be correct and still unusably slow:** WF-1B's exact Clopper-Pearson took over an hour per real report; full-size profiling on invented data found it in minutes (PERF-1). Profile at full size before the owner's first real run.
- **A claim the record repeats is still checked against the code** (MHUP-1): "no released method uses its target's draw number" was repeated through the stock-take until a cold read found the target in every tie-break key and view digest; the record was corrected (register v0.24).
- **A cold read by a fresh helper before every review round pays for itself** (MHUP-1, five rounds): it found that E_1 revision 2 refuses every new mode; a later-released method could never pass the holdout draws; partial forecast sets would be orphaned after a clean session end; the install preflight ran a tool not yet installed; a nested launch would create the "never-existing" byte-code folder (reproduced on CPython); the updater lock was released before the release record. Give the helper the reviewer's findings, the old and new editions and the diff, ask for scenario traces, and send it a recheck after the fixes; run it on Opus to save Fable.
- **State machines need every exit enumerated** (EX_127 B01-B03, EX_129 C01): crash at each step, resume under the same identity versus a successor, roster changes between start and finish, a clock-based rule judged twice. Persist each judgement as a record (tickets, `SET_STARTED`) instead of recomputing it, and write the event-order table before the prose.
- **Check what an existing tool really does before relying on it** (EX_129 B02): the updater's own create-exclusive lock (`results_master_v0_1.py` lines 657-663, taken at line 686 before the fetch) became the install's barrier with no code change, and its browser-driven fetch (line 567) meant a redirect could only be refused after the fact.

- **Mutation honesty:** "no test plants it" is non-detection, not equivalence; print each equivalent's reason. Token economy: new mutants alone with `--only`, then one final chain; after a one-line change rerun only the changed module and say so.

## 9. Adding a new method (the process from here)

CODE-1 and CODE-2 give every method the release gate, create-only publication, receipts and traceability. A new method needs only its own pieces, and starts from the template, `doc/METHOD_TEMPLATE/` (draft 5; README and checklist), as every method since E_6 has:

1. **The idea, in the owner's words:** what it looks at and what it predicts. Decide its identity: an existing catalogue method (E_2..E_62, now `FORMULA_OPEN`, variant `NOT_YET_SPECIFIED`), or a new identity E_63 or later, which is OPEN and needs an owner decision and a catalogue amendment first.
2. **A short specification** (Claude drafts; reviewer R-3; owner ratifies): the exact rule; its views and channels (UNORDERED_SET / OPERATOR_DRAWN_ORDER, dates or not); its variant ID; its outputs (ranking, TOP and WORST per channel, probability kind per channel, any diagnostic record); insufficient-history behaviour; whether it needs seeds (if so, the seed-policy package comes first); and its plain-English text (D-3). **Fix every variant's settings here, before code** (E2R-R14A). Check it against the owner's philosophy (section 2A): no number suppressed, no veto.
3. **One code package** (HIGH; R-2 reproduction; owner's Windows run): its folder `src/methods/E_<nnn>/` with `contract.py` and `IN_DEVELOPMENT.txt` (no entry file, D6-1), any shared helper in `_common/`, a `METHOD_DECLARATION_V1` and a `FORMULA_OPEN` registry entry for each variant in each game (generated by a script that travels with the package), the `ADAPTERS` line in `Method_Contract_Runner.py` (an edit to an existing file, listed and checked), synthetic tests including T-05 and each variant's own setting computed in the test, and mutation checks. The register text rides in the same round. It installs non-runnable, after a Claude Code rehearsal.
4. **Release** (a separate small reviewed package; the owner's two actions, as REL-1 did for 39 variants): delete the flag; append a `SUPPORTED` entry for the same declaration. Then the method can run through the contract runner. **Since MHUP-A (installed 13 November 2026)** every install also writes an install record (code arrival) and every release a release record, after COMMITTED PASS, as a second commit (design 4.3, Appendix J; `src/package_tools/install_records.py`); a variant's release date is its release record's local date, which decides whether its catch-up forecasts count as CATCH-UP or as development evidence. A variant released after 13 November 2026 is never part of Mode H's fixed cohort: it can never claim a fresh evaluation on the ten holdout draws (owner, 13 November 2026).
5. **Real data:** with `ENABLE_CONTRACT_REAL_DEVELOPMENT` on (WF1-3), a released method joins the next walk-forward batch the owner authorises; a batch holds the full cohort (ER-6), so a new method means a new batch per game, then a report. **Once the weekly session runs** (MHUP-B), a newly released variant joins the session roster at its next session and is first forecast at the first target frozen after its release; it never forecasts a holdout draw or an earlier closed target; its back-history over post-holdout draws, if wanted, is a separately identified development batch (design 6.3; roadmap 21b). A roster-changing install is refused while a weekly forecast set is unfinished (design Appendix J). Preregistration stays a separate gate.

**Keeping the template current** (owner, 30 October 2026): whenever a method's design, review, code or install shows something the template should say or do differently, in Claude's assessment or the reviewer's, Claude proposes the template update in the next package. It is reviewed like any other document, and its draft number goes up. Each method's handback says whether it found anything for the template.

### 12.2 The tools (`exchange/CLAUDE_WEB_TOOLS/`)

Guarded paths are files that must stay byte-identical in Git (their base blob hashes are written into the verifier).

### 12.3 Building and rehearsing a package

- **Base tree:** `git archive <base commit> | tar -x -C BASE`, then delete `source_data/`, `results/` and `transitory_data/` from it. **Dev tree:** a copy of the base tree plus your changes. Never work in the owner's checkout.
- **Suite on Linux:** `PYTHONPATH=src:src/methods:tests python3 -B -m unittest <module>` per module, on the system Python 3.13 and on a Python 3.15 venv with the project's dependencies. The 3.15 venv will not exist in a new workspace: `uv python install 3.15`, `uv venv --python 3.15 <dir>`, then install the project's direct packages, as listed in `DIRECT_PACKAGES` in `install_upgrade_dependencies_into_venv.bat` (`requests beautifulsoup4 psutil numpy scipy threadpoolctl selenium pyahocorasick`; nothing of the project imports `pyahocorasick`, so the suite does not need it; `requirements.txt` is historical), with `uv pip install --python <dir>/bin/python ...` (a bare 3.15 fails every module on `numpy` and `psutil`). ### 12.5 Traps in the cloud workspace

- **Stopping your own test jobs in the cloud workspace, and nothing else (EX_117 C02).** This applies only to expendable, non-scientific test processes that Claude itself started in its own cloud workspace for this chat (a test suite, a rehearsal, a mutation run, a profile). Never stop them by a name pattern: `pkill -f unittest` matched the chat's own shell twice and killed it. Find the job you started (`ps -eo pid,ppid,etime,cmd`), confirm from its parent and its full command line that it is that job, and stop only that one; if you are not certain, let it finish. **A PID is neither proof of ownership nor permission to stop anything else.** Claude never terminates a project process: no experiment, worker, coordinator, batch, report or uncertain process, on any machine. The protected no-status/no-kill interlock (Architecture section 5C; section 5.4 above) and the owner's separate process-control gates govern those, and nothing on the owner's computer is ever stopped by Claude.
- **The shell tool's default timeout is about two minutes.** Give a longer timeout, or run long jobs in the background (`nohup ... &`) writing to a file, and poll the file with short sleeps.
- **Do not import a package's own scripts in place** for a probe (a `__pycache__` folder crept into a package and had to be removed and the package rebuilt); copy the script elsewhere or load it with Python's `-B`.
- **The shell resets its working directory** after some commands; use absolute paths.
- **Outbound network** goes through a proxy allowlist (package registries and GitHub); lottery sites are never contacted, and must not be tried.
- **Downloaded or received files** go into a fresh directory each; run Python that reads them with `-I`.
