## 1. What this is, and what it is not

The owner authorised MHUP-A development in two review slices followed by one integrated install package (EX_140 section 3). This is **slice 1**: the foundations every later MHUP-A function stands on. It is a **review package, not an install candidate**: it carries no installer, verifier, release record or task file, and nothing here is to be installed. The integrated package, after both slices are reviewed, will carry the usual whole-file overlay, pre/post/committed verifier, suite runner, LF and CRLF rehearsals and the Claude Code task file (T016). Nothing in this slice is real-data work: every test runs on invented masters in temporary folders; the holdout statement is in section 7.

The base tree is `main` at `2061055` (`git archive`, data folders excluded). `MHUPA_Slice1_Review_v1.zip` holds the complete set of changed and new files as they stand in the development tree (`overlay/`), the scripts that build that tree from the base by counted edits (`tools/`), the suite runner with the new expected counts, the mutation tool, and the Linux evidence (`evidence/`). `mhupa_slice1_src_tests.diff` is the complete diff of `src/` and `tests/`, base to development tree; the archive and registry additions are listed in section 2(h) with their digests.

## 2. The change, by rule

**(a) `_common/master_versions.py` (new): the version-2 master rules (design 3.2 rules 1, 2, 3; EX_125 C01).** Orchestration only: nothing it returns enters a DrawView, a permitted-view digest or a method task.
- Rule 1, the closed ledger grammar (`parse_ledger`): row 1 is `INIT` covering exactly the development prefix; every later row is `UPDATE` or `NO_CHANGE`; versions are 1, 2, 3, ... with no gap; `utc` never decreases; the cross-row rules (`NO_CHANGE` repeats the previous hash, counts and last draw with no added range or backup; `UPDATE` adds a consecutive range starting at the previous last draw + 1, names the previous master as its backup, and carries a new hash); the header is the updater's `LEDGER_COLUMNS` (the module holds its own copy; a test asserts equality with `src/results_master_v0_1.py` read by `ast`, never imported). Anything else refuses with `LedgerRefused`.
- Rule 2, prefix-verified pins (`verify_master_against_ledger`, `resolve_pin`): the whole file hashes to the last row; for every row, the first `1 + draw_count` lines (each with its own line ending, `splitlines(keepends=True)`) hash to that row's `master_sha256`, the last of those lines starts with `last_draw`, and no line follows the last row's. A pin (`ledger_version`, `master_sha256`) resolves only to the row with that version and exactly that hash.
- Rule 3, the target gate (`target_admissible`): from version v, targets in `first_draw + 1 .. last_draw(v) + 1`. The holdout condition is applied by the callers (reader, validator, dispatch gate, runner), not here.
- **The one-row leniency.** When the ledger has a single `INIT` row, the module applies today's checks exactly as every reader did before it (the whole-file hash and the INIT verification record), and not the full grammar or the line-count rules. This is why every existing synthetic fixture (seven-column ledgers, `utc=fixture`, masters shorter than the INIT counts) and the committed version-1 records pass without a byte changed. The full grammar applies as soon as the ledger has two rows, which is the first thing the owner's updater will ever produce. The reviewer may wish to confirm this is acceptable; the alternative (rewriting every fixture) was judged a larger change for no gain in safety, since a one-row ledger has no cross-row rule to check.
- `load_verified_source` / `current_pin` / `check_source` read through the reader's trusted-file helper (regular file, no symlink), which `outcome_reader` and `walk_forward` also use; no other module opens a master (the L-U5 static test lists the eight files that name `_results_master`).

**(b) `_common/game_draws_reader.load_pinned_draw_view`:** the manifest's `ledger_version` is any positive integer; the source is checked by (a); the pin resolves by version and hash; the target gate of rule 3; a target at or above `holdout_first` additionally needs the game's valid opening record (`owner_records.opening_record`, design 4.2). The legacy Powerball 1577 forecast-only exception is unchanged. `_parse_prefix` and `DrawView` are unchanged: T-05 rerun on a version-3 synthetic master gives byte-identical views and digests for every development target under a version-1 pin and under the current pin.

**(c) `evaluation/outcome_reader._verify_source` (design 3.2 rule 5):** the same chain and pin checks; the pinned version's own bytes (its prefix) are served, never the grown file. `read_outcomes` and `report.py` carry `ledger_version` through from the plan. `_check_targets` still refuses every target at or above `holdout_first`: the freeze-before-outcome rule (design 5.3) belongs to slice 2's scorer, so until then no outcome of a holdout draw is readable by any project code (section 7).

**(d) One data kind (design 3.3; owner decision MHUP-Q10): `contract_task.view_data_kind`, E_1 revision 3, the adapter.** `view_data_kind(run_mode)` maps every real mode (`REAL_MODES` and, when slice 2 adds it, `CATCH_UP`) to `REAL_VIEW_DATA_KIND` and leaves synthetic modes as they are. The E_1 adapter passes `data_kind=view_data_kind(task.run_mode)`. E_1 revision 3 (`E_001/multigame_e1.py`) accepts the two view kinds and never a run mode, refuses a training view whose length is not `target - first_draw`, and leaves the target ceiling to the shared gates; counting, ranking and tie order are byte-for-byte revision 1's and 2's. The legacy standalone runner's release check names revision 3. Revision 2 is archived complete under `archive/methods/E_001/r2/` by `package_tools.method_retirement.retire` with the README it writes; the registry gains `entry_0003` (SUPPORTED, revision 3, `previous_entry_digest` of entry 2) and declaration `r3.json` (entry 2's declaration with `method_revision` "3") in both games. See the OPEN point on `effective_date` in section 6.

**(e) The structural rules (design 3.4(a)): `contract_records`, `contract_vocab`, `contract_forecast`, `contract_receipts`.** `RUN_REQUEST_V1` gains the optional key `binding` (one of three closed shapes: `MODE_H_BATCH` with `batch_id` and `plan_digest`, `WEEKLY_SESSION` with `session_id` and `session_digest`, `OWNER_DIAGNOSTIC`; the first two name their own request's `run_id`). The mode/target/binding table: synthetic, benchmark and in-sample modes stay within the development prefix and carry no binding; `REAL_DEVELOPMENT` within the prefix is unbound or diagnostic, above it session-bound (target after the holdout) or diagnostic; `REAL_HOLDOUT` names a holdout draw and is `MODE_H_BATCH`-bound only; `FINAL_NEXT_DRAW` and `CATCH_UP` name a draw after the holdout and are session-bound (unreachable in this slice: `FINAL_NEXT_DRAW` stays reserved and `CATCH_UP` is not yet a run mode; slice 2 opens them). `REAL_HOLDOUT` is unreserved as MHUP-R wrote it: `producible('REAL_HOLDOUT', FORECAST) == ('WF_FORECAST', 'HOLDOUT_MODE_H')`; its diagnostic product stays refused (OPEN, section 6). `ledger_version` is any positive integer in requests and receipts. A forecast record's target is checked by its mode (holdout range for `REAL_HOLDOUT`; after the era's first draw for the other real modes; the development prefix otherwise).

**(f) Publication admission (design 3.4(b)) and barrier P (Appendix J): `contract_dispatch`, `owner_records.py` (new).** The dispatch gate reads, at the fixed project root (`PROJECT_ROOT`, patched only by test harnesses; no caller-supplied authority, E2RC2-B01/B02), the owner's value-free records: for `MODE_H_BATCH` the game's one plan (digest must match the binding; the pair must be listed; no lifecycle marker; no DONE ticket for the pair; an OPEN ticket naming this run id, pair and exact request digest, not closed by a later `DONE` or `FAILED_TO_START` for that run id; and, for `REAL_HOLDOUT`, the opening record); for `WEEKLY_SESSION` the session record (digest), the roster entry, the developed record (GOAL-1), no freeze line for the target, no DONE ticket for the pair in any session ledger of the game, an open ticket, and the release-date rule (`REAL_DEVELOPMENT` only for a variant released on or after the draw's derived date; `CATCH_UP` only before it); for `OWNER_DIAGNOSTIC` (decision MHUP-Q11) `REAL_DEVELOPMENT` only and, for a holdout or later target, the opening record and the Mode H seal. Refusal codes: `BINDING_NOT_RESOLVED`, `PAIR_NOT_IN_PLAN`, `BATCH_CLOSED`, `PAIR_ALREADY_DONE`, `NO_OPEN_TICKET`, `HOLDOUT_NOT_OPENED`, `NOT_IN_SESSION_ROSTER`, `NOT_DEVELOPED`, `TARGET_FROZEN`, `MODE_DISAGREES_WITH_RELEASE`, `DIAGNOSTIC_MODE`, `MODE_H_NOT_SEALED`, and `INSTALL_IN_PROGRESS` while `contract_data/INSTALL_IN_PROGRESS.txt` exists (every dispatch-gated run, the legacy gate included). `owner_records.py` holds the schemas, paths, readers and ticket rules (OPEN / DONE / FAILED_TO_START / SET_STARTED / RESUMED; JSONL with the torn-last-line rule: a final line without its newline is ignored and reported) that slice 2's writers will use; this slice ships readers only. The records' writers (`Method_Mode_H.py`, the weekly program, the install tool) are slice 2.

**(g) The runner (`contract_runner`) and the launcher (`Method_Contract_Runner.py`).** A real-mode run reads only the project root; a bound run publishes only under its binding's root (`results/real/holdout/<game>/contract_runs` for Mode H, `results/real/diagnostic/contract_runs` for the diagnostic route, `results/real/weekly/contract_runs` for a session), refused as `DATA_SOURCE_REFUSED` before anything is read; after the reader has verified the chain and the pin, a `MODE_H_BATCH`- or `WEEKLY_SESSION`-bound request must pin the ledger's current last row (`STALE_PIN`, a `DATA_ADMISSION_REFUSED` terminal with no forecast). The command line gains `--ledger-version N` (required) and `--binding OWNER_DIAGNOSTIC`; `REAL_HOLDOUT`, `FINAL_NEXT_DRAW` and `CATCH_UP` are refused at the command line with exit 2 (official runs are bound and ticketed by the walk-forward driver or the weekly program only); `--binding` with a synthetic mode is a usage error. `walk_forward.ledger_pin` returns the current `(version, master_sha256)` and the plan records `ledger_version` from it.

**(h) Files added outside `src/` and `tests/` (not in the diff; in the overlay).** `archive/methods/E_001/r2/` (seven files, byte-equal to the base tree's live revision-2 files, and `README.md`); `src/methods/_common/contract_data/declarations/<GAME>/E_1/FULL_HISTORY_RAW_COUNTS_V1/r3.json` and `.../registry/<GAME>/E_1/FULL_HISTORY_RAW_COUNTS_V1/entry_0003.json` for both games; `tests/fixtures/e1_r2_reference_v1.json` (section 3). Their digests are in `MHUPA_Slice1_Review_v1_zip_members.txt`.
