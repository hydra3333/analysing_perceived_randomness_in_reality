## Terms used in this note

- **MHUP-1:** this work item (Mode H, the results Update and the Prospective mode). **MHUP-A, MHUP-B:** its two code packages (section 8).
- **Mode H:** the one-time test on the ten sealed holdout draws per game (Powerball 1577-1586, Oz Lotto 1694-1703).
- **The master:** a game's results file, `source_data/<GAME>_results_master.csv`; **the master ledger:** its append-only version list, one row per updater run. **The forecast ledger**, **the witness ledger** and **the score ledger** are new weekly records (sections 6.5, 6.6). R3's **outcome record** is the master row that supplied an outcome, identified by master version and SHA-256; R3's **evaluation record** is the score ledger (6.6).
- **"Version 1 only":** today every reader accepts only the first (INIT) master version. **The version-2 rules** (section 3) accept version 2 and every later version.
- **Freeze** has three senses, kept apart: the **plan freeze** (the study manifest and code fixed before the holdout is opened, 4.1); a **frozen forecast** (a method's run record, published create-only, as today); a **freeze line** (one line of the forecast ledger saying every variant of the session's roster has a ticketed DONE record for a target, 6.5).
- **DONE, COMPLETE:** the driver's terms for a planned run that ended in a continue class, and for a batch all of whose runs are DONE (5.2).
- **Binding:** the block in a run request that names the Mode H batch or the weekly session the run belongs to, or declares the run an owner diagnostic; the gates resolve it at fixed paths (3.4). The requests that need one are `REAL_HOLDOUT`, `CATCH_UP`, `FINAL_NEXT_DRAW`, and `REAL_DEVELOPMENT` with a target above the development prefix; `REAL_DEVELOPMENT` within the prefix (today's batches) and the synthetic modes carry none, as today. An **unbound** request of the first kind refuses to publish.
- **Ticket:** a value-free line the driver or the forecasting half appends to its batch's or session's **attempts ledger** before a run (open) and after it (DONE, or FAILED_TO_START when a resume finds an open ticket whose run never completed), naming the run id and the pair; the dispatch gate admits an official real-mode run only with an open ticket and never a second one for a pair that has a DONE ticket in **any** attempts ledger of the game (3.4). A weekly set's start is also a ticket (`SET_STARTED`, 6.4). An official record is a ticketed DONE record; nothing else is ever named by a plan roster or a freeze line.
- **Diagnostic route:** the owner's hand-typed re-test, a `REAL_DEVELOPMENT` run with the `OWNER_DIAGNOSTIC` binding, published under its own root and never scored into any ledger (3.4, Q11).
- **Lifecycle markers; seal:** value-free, create-only files in a game's Mode H batch folder, in a fixed order: `BATCH_COMPLETE`, `SCORING_STARTED`, `SCORE_COMPLETE`, `MODE_H_SEALED` (the **seal**); the dispatch gate refuses any holdout publication once any exists, and the updater refuses, after the one permitted first update, until the seal exists (5.2, 4.1).
- **Session:** the weekly command's unit of work for one game, with its create-only session record, its attempts ledger and its session lock (6.1). Every new publication of a session pins the master version the session record pins and requires that pin to be the ledger's current last row; if the master has grown, the session ends `STALE`. An interrupted session is **resumed** under the same id; scoring an older session's freeze line from a later session is permitted under the cross-session rule of 6.3.
- **Roster:** the released, unretired variants at `open-session` (the **session roster**, in the session record; a variant is retired when its registry chain entry is superseded or marked retired by an installed package, 4.3) or the variants a freeze line names (the **line roster**: the writing session's roster plus every variant with an earlier session's ticketed DONE record for that target; fixed for ever when the line is written). A target is closed under its line roster, never under a later one (6.3). **Rosters change only through an install** (release records, retirements), and a roster-changing install refuses while any weekly set is unfinished (a target above `holdout_last` with a weekly ticket and no freeze line; Appendix J, the install check), so every session that touches an unfinished set has the same roster as the session that started it (EX_129 C01).
- **Exit words** of the forecasting half's `next`, each derived from the persisted records and the clock, never from memory of an earlier run: `FROZE N` (N's freeze line exists), `FROZE_NEXT M` (the next draw's line was just written), `OPEN M` (the next draw's line exists and its result is not accepted), `NONE` (no set for the next draw may start now), `STALE` (the master grew); `CLEAN` is the process tool's verdict (6.1, 6.3).
- **Install record; release record:** the install record says a package's code arrived (POST PASS); the release record, written after COMMITTED PASS with E and P removed and while the install still holds the updater lock, says its variants became released; MH-1's release date is the release record's local date (4.3).
- **Evidence tier:** the label a scored record carries: `HOLDOUT_MODE_H`, `PROSPECTIVE`, `CATCH_UP` (new) or `DEVELOPMENT_WF_EXPLORATORY` (R3 17.3.9; MH-1). **Effective class:** what a report counts a record as, derived by the total rule of Appendix I from the tier, the deadline, the outcome timing and the release evidence; one record's effective class can be `LATE_PRE_DRAW` (new; an operational category, never counted as evidence of any tier). "Development" has two senses: the development **prefix** (draws before the holdout, R3 6) and the development **tier**; 3.2 rule 3 and 6.4 keep them apart.
- **Publication status:** `PUBLISHED_BEFORE_DRAW` or `TIMELINESS_UNVERIFIED` (R3 10.5), derived at report time from the witness ledger (6.5); never stored in a frozen record or a score line.
- **Q1 to Q11:** the owner's questions, listed with their answers in section 9.
- **R-4 oracles:** the reviewer's right to independent reference checks (exact-arithmetic or independently built fixtures) for high-consequence code (agreed position; H-1 1.4).

## 0. The whole thing in plain English

Today the system can only look at draws before the holdout. To make real next-draw forecasts we need five things, in this order:

1. **Read a master that has grown.** Every reader today refuses the master as soon as it has a second version (finding A1): even an update that finds nothing new writes a NO_CHANGE line and stops everything. The first job is a reader that accepts later versions, checks their history, and still serves each forecast only the draws before its target.
2. **Let E_1 take part.** E_1's installed revision 2 refuses, in its own code, every run mode except development and every target beyond the development cap (section 2). It gets a revision 3 with the same arithmetic and wider admission, in the first package, under the one-package exception the owner has extended to it (Q10).
3. **Open the holdout, once, on the record.** You freeze a study plan (which methods, which measures, every file of code and every launcher, every installed package), then write the opening record. Only then does the updater add the holdout draws and every later draw, once; nothing else may change until Mode H is scored.
4. **Mode H.** Every released variant forecasts each of the ten holdout draws, each from the draws before it (the reader hands a method nothing from its target draw or later: that is what "N-1 isolation" means below), inside one owner-approved batch that every run must name. No forecast is scored until every planned run is finished; then the ten draws are scored once. Powerball 1585 and 1586 carry their exposure flag and count fully. This is **option A, the owner's decision of 3 November 2026**: a precommitted holdout evaluation, not pre-draw forecasting, and every record and report says so.
5. **The weekly session (MH-1).** Per game, one command you type. It works through every draw that has a result but no score, one draw at a time and exactly in MH-1's order: forecast N from the draws before it, reveal N, score N, then N+1; then it freezes the next draw's forecast before that draw's deadline. Inside the command, a small sequencer runs two separate programs in turn, one that forecasts and one that scores, so methods and the scorer stay apart. Everything runs offline; the timing proof is a local, chained record; a GitHub push is an optional witness whose status is worked out at report time.

The draws in view (from the weekly calendar rule): the planning target is **Oz Lotto 1709 on Tuesday 17 November** and **Powerball 1592 on Thursday 19 November** as the first forecasts frozen before their draws (in practice by 23:00 the evening before, because the command stops starting a forecast within the last hour before midnight); the week of 9 November is a stretch only. Whatever the first session's date, the catch-up covers every draw since the holdout. For the 39 variants released on 31 October 2026, Oz Lotto 1704-1706 and Powerball 1587-1589 are development evidence (they predate the release) and Oz Lotto 1707 onward and Powerball 1590 onward are CATCH-UP; for E_1 revision 3 the boundary is its own release date (section 2).

## 1. Mode H: the reading of "frozen before the holdout is opened" (Q1, decided)

Register v0.23 ("Terms for that design") and H-1 section 10 describe Mode H as: every released variant forecasts each of the ten holdout draws **walk-forward (each from the draws before it)**, **all frozen before the holdout is opened**, then scored once. Both halves cannot hold literally: the forecast for Powerball 1578 must be trained on draw 1577, which is itself a holdout draw. The stock-take round weighed three readings; the owner decided **A** on 3 November 2026, after the reviewer's EX_125, which provisionally favours A (O01) provided B01, B04 and C05 are met (addressed in sections 3.4, 4.1 and 5.3; EX_127 O01 supports A conditional on its B03 and B04, addressed in 5.2 and 4.1).

- **A (decided):** the study plan and code are frozen before the holdout is opened; the holdout is opened and added to the master, once; then one Mode H batch forecasts all ten targets, each method seeing only the draws before its target (the N-1 rule, which test T-05 already proves); every planned run is DONE, and every published forecast frozen create-only, before any approved scoring process reads any holdout result; then the ten are scored once. Its honest description, used throughout: **a precommitted holdout evaluation with N-1 isolation, not pre-draw forecasting**; the outcomes are already in the system when the forecasts are made, held away from the methods by the reader (R3 17.3.5, line 1130: "historical evaluation, not advance-frozen prospective forecasting"). Neither A nor B makes already-public outcomes prospective (EX_125 O01).
- **B (not chosen; kept described truthfully):** for each target in turn, freeze every forecast for N, then release N's result, score N, move on. It buys a local timestamp ordering between each freeze and each release, at the cost of a staged release of the master, a predating check, and recovery rules in the most protected code.
- **C (withdrawn):** forecast all ten holdout draws from the development draws only, freeze, then open and score. The target is not a scientific input of any released method (the driver runs unordered, date-free views: `walk_forward.py` lines 45 and 143-144), but it does enter every method's tie-break key (`contract_records.py` lines 405-409), every non-legacy view digest (`game_draws_reader.py` line 125) and E_1's own tie key (`E_001/multigame_e1.py` lines 23 and 50). Under C the ten forecasts from one prefix would have identical scores and could differ only in the order of tied numbers: a fixed-origin test of one scoring, not of the retraining process. In plain words: C would test the same forecast ten times. The corrected reason is on the roadmap and in the stock-take record (v0.8).

**The primary statement Mode H supports (for the register amendment):** "a locked holdout study: the study plan, the code and the environment were frozen before the holdout was opened; every forecast used only draws before its target; all planned attempts, and every successfully published forecast, were frozen before any scoring process read a holdout outcome." Register v0.23's sentence "all frozen before the holdout is opened" is to be read, and in register v0.24 amended, to this wording (EX_125 C04: "all planned attempts", not "every pair produced a forecast"). Q1 is **OWNER-DECIDED** (3 November 2026) as an input; the design as a whole is ratified after this recheck.

### 3.2 The version-2 rules

One shared, orchestration-only module, `src/methods/_common/master_versions.py`, used by every file in the table above. Nothing in it reaches a method; its outputs never enter a `DrawView` (the B1 rule holds). It carries its own copy of the updater's `LEDGER_COLUMNS`, with a test asserting equality with `src/results_master_v0_2.py` (the owner's tool is not imported by project code). `tests/test_wf1b_static.py` lines 12-14 (`ALLOWED_COMMON`) gains `_common.master_versions`.

1. **Ledger chain check (the closed grammar; EX_125 C02).** The header equals `LEDGER_COLUMNS` exactly, in order. Every row has every column; versions are the integers 1, 2, 3, ... in order with no gap, no duplicate and no extra or truncated line; `utc` parses as an ISO-8601 UTC instant and never decreases; `first_draw` equals the profile's first draw in every row; `master_sha256`, `grab_sha256`, `backup_sha256` and `tool_sha256` are 64 lower-case hex digits where present; `tool_version` is non-empty; `note` is free text, ASCII only. Row 1 is the INIT row with today's checks of its own fields (action, counts, first and last draw, the INIT verification record); the one change is that the run's pin is now bound to its own row v (rule 2), not necessarily to row 1. Every later row is:
   - `NO_CHANGE`: the same `master_sha256`, `last_draw` and `draw_count` as the row before; `added_count` 0; `added_first`, `added_last`, `backup_file`, `backup_sha256` empty; `grab_file` and `grab_sha256` present (the grab itself is not required to exist: it is a local, untracked file);
   - `UPDATE`: `added_count` >= 1; `added_first` = previous `last_draw` + 1; `added_last` = `last_draw` = `added_first` + `added_count` - 1; `draw_count` = previous `draw_count` + `added_count`; `backup_sha256` = the previous row's `master_sha256`; `backup_file` and `grab_file` present;
   - any other `action`, or any broken rule: refuse. The INIT verification record is checked as today.
   This is **cross-row consistency**, not a cryptographic chain of the ledger itself: the rows are plain CSV. The cryptographic link is rule 2, which binds every row to the bytes of the current master.
2. **Prefix-verified pins.** Because the updater only appends and re-serialises with the same function, version v's bytes are an exact prefix of every later version. The reader checks **every row** against the current master: the SHA-256 of the first `1 + draw_count(row)` lines (the header and that row's draws, each with its CRLF) must equal the row's `master_sha256`; the first field of the last of those lines must equal `last_draw(row)`; and the whole file's SHA-256 must equal the last row's. A run pins `(ledger_version v, master_sha256 s)`: every run of a session or batch pins the current last row; the pin is accepted when row v exists with that SHA-256 and passed the prefix check. **Two pins per scored forecast** (EX_125 C02): the forecast record pins its training master version; the score line pins the master version that supplied the outcome; the two need not be the same and both are kept. Consequences:
   - the committed batches and reports (pinned to version 1) stay verifiable after any update;
   - a `NO_CHANGE` row needs no special handling;
   - a later change to any earlier row (a correction) breaks the prefix check and every run refuses: corrections need their own reviewed design (R3 10.3); this note does not provide one;
   - an update interrupted between the master replace and the ledger append (finding A7) leaves a master whose SHA-256 matches no row: every reader refuses, as does the updater's own next run (`load_verified_master`, lines 298-300). Recovery is in section 7.
3. **The target gate** (replacing `historical_development_target_allowed` as the run-time gate in every file of the table): for a pin to version v, targets up to `last_draw(v) + 1`; a target at or above the game's `holdout_first` additionally needs a valid opening record for that game (4.2) **and** the mode gates of 3.4. `historical_development_target_allowed` stays as the **definition of the development prefix** and is what the mode gates use; E2R-R52's "hard-coded target ceilings (now the profile's `historical_development_target_allowed`)" and R3 6's "development caps remain 1576/1693" are amended to this reading in the register. The E_1 1577 legacy exception is unchanged.
4. **What does not change.** The prefix parse (`_parse_prefix`, lines 161-209) still reads no data column of the target or any later row. View schemas and digests are unchanged for every existing run.
5. **The outcome reader** uses the same chain and pin rules and serves targets up to `last_draw(v)` only, and only under the freeze-before-outcome rule (5.3).

### 3.3 One data kind for every real mode

`contract_task.view_data_kind` (lines 45-46) maps `REAL_DEVELOPMENT` to `REAL_HISTORICAL_DEVELOPMENT` (`contract_task.py` line 17) and any other run mode to its own name; the data kind is part of the permitted-view digest, which feeds every tie-break. ### 3.4 The gates: structure, publication and scoring kept apart (EX_125 B01; EX_127 B01, B03, C01)

Three different things are decided by three different parts, with no caller-chosen authority (E2RC2-B01, B02). The one new idea since v0.1r2 is the **ticket**: before the driver or the forecasting half starts a run, it appends one value-free line to its batch's or session's attempts ledger naming the run id and the pair; the dispatch gate admits an official real-mode run only if its ticket is there and open. A hand-typed run has no ticket of its own and cannot become official by mistake: it would have to copy the run id of a live open ticket, and a resume marks every open ticket of a run that never completed `FAILED_TO_START`, and writes the DONE ticket for one whose run folder proves it completed, before any new ticket is written (Q11); the window in which such a copy could be admitted is therefore from a run's open ticket to its DONE ticket, or to the next resume after a crash.

- **(a) Structural validation** (`validate_run_request`, the forecast header, the receipts): a request that needs a binding (Terms) must carry one of three kinds: `{kind: MODE_H_BATCH, batch_id, plan_digest, run_id}`, `{kind: WEEKLY_SESSION, session_id, session_digest, run_id}` or `{kind: OWNER_DIAGNOSTIC}`; its shape and the mode-to-target-range rules are checked here: `REAL_HOLDOUT` only for targets in `[holdout_first, holdout_last]` and only with a Mode H binding; `CATCH_UP` and `FINAL_NEXT_DRAW` only above `holdout_last` and only with a session binding; `REAL_DEVELOPMENT` above the prefix with a session binding only above `holdout_last`, and with the diagnostic binding anywhere the pin allows (below); synthetic modes and `REAL_DEVELOPMENT` within the prefix carry no binding and are unchanged. The mode-to-pin rule is checked where the pin is read (the runner, through the reader): `FINAL_NEXT_DRAW` only for target = `last_draw(v) + 1` of the pinned version v (so a `FINAL_NEXT_DRAW` record can never exist for a draw whose result the pinned master already holds); `CATCH_UP` and `REAL_DEVELOPMENT` above the prefix only for targets at or below `last_draw(v)`; and **every official weekly or Mode H publication requires the pin to be the current last ledger row** (a grown master fails every further publication of a session: `STALE`, 6.3).
- **(b) Publication admission** (the dispatch gate, `contract_dispatch.py`, which already reads the installed registry and no draw data, E2R-R23A): resolves the binding at fixed roots derived from the project root, reading only value-free records:
  - a **Mode H binding** must name the game's one plan (5.1), with that digest, listing this exact (game, method, revision, variant, target); the run id must have an **open ticket** for that pair in the batch's attempts ledger and the pair must have **no DONE ticket**; and none of the batch's lifecycle markers `BATCH_COMPLETE`, `SCORING_STARTED`, `SCORE_COMPLETE`, `MODE_H_SEALED` (5.2) may exist; a `REAL_HOLDOUT` request additionally needs the opening record. So no second record for a pair, and nothing at all once the batch is complete or scoring has begun;
  - a **session binding** must name an existing session record (6.1) for this game, with that digest, listing this variant as active with its release date; the run id must have an open ticket in the session's attempts ledger and the (variant, target) no DONE ticket in **any** attempts ledger of the game (fixed root, every session's ledger read); the game's forecast ledger must hold **no freeze line for the target**; the game's developed record must exist; the mode must agree with the install evidence in the session record: `CATCH_UP` only if the variant's release date is before the target's draw date, `REAL_DEVELOPMENT` above the prefix only if it is not;
  - a **diagnostic binding** (Q11, the owner's re-test route) is admitted for `REAL_DEVELOPMENT` only, for any target the pin allows (`<= last_draw(v)`), and for any target at or above `holdout_first` only with the opening record and the game's `MODE_H_SEALED` marker (a sealed holdout is ordinary history; before the seal no diagnostic run trains on or targets an unsealed draw); it publishes under the **diagnostic root** `results/real/diagnostic/contract_runs/`, which no plan, freeze line or scorer ever reads, so such a record is never official and never scored into any ledger. The barriers also live here: the orphan marker and, during an install, `INSTALL_IN_PROGRESS.txt` (Appendix J).
  **A request that needs a binding and has none, or whose binding or ticket does not resolve, refuses before anything is read and publishes nothing.**
- **(c) Scoring rights** (the evaluator): the freeze-before-outcome rule (5.3) and the binding check repeated: a record is scored only if its binding and ticket resolve and it is **the record the plan's roster or the freeze line names for its pair**: the ticketed DONE attempt (there is exactly one, by (b)). Diagnostic records are never named by a roster or a freeze line.

The ticket makes the official path exact (only a run registered beforehand by the driver or the forecasting half), and the diagnostic binding gives the owner his re-test route: `Run_Experiment.bat Method_Contract_Runner.py run --mode REAL_DEVELOPMENT --binding OWNER_DIAGNOSTIC ...` publishes a development-tier record under the diagnostic root; `Run_Evaluation.bat Method_Weekly_Score.py diagnostic-score --run <run id>` prints that record's per-target quantities to the console against an accepted outcome (never a holdout outcome before the seal) and writes nothing to any ledger. ### 4.3 Install and release records (Q5; owner-ratified mechanism, 2 November 2026; EX_127 C05)

MH-1 makes a catch-up forecast valid only if the method revision was installed before that draw's date; OFF-1 says this is checked against local install records, not Git history (E2R-R54: Git history is never relied on). Design, with the release event made its own record (EX_127 C05):

### 5.2 One batch only, DONE, COMPLETE, and the sealed study (EX_127 B03)

One Mode H plan per game (the batch-id record above); a second plan is refused. The report carries the attempt id and no wall-clock field, so the resumed and the uninterrupted paths give the same report bytes. A second routine attempt is refused only when `SCORE_COMPLETE` exists; before that, the same attempt resumes. The ratified corrective exception (a separately identified scoring run beside the first, to correct a scorer fault or add a measure) is allowed after the seal, under its own identity, and never touches the first ledger.

### 6.2 The status block (EX_127 O02)

The forecasting half's `status` prints, per game, before anything else: the authoritative **last accepted result version** (the ledger's last row, its version and `last_draw`); whether a session lock exists and for which session (a recovery interlock that must be resolved or resumed before a new session); per variant, summarised, the last draw with a ticketed DONE record and the last scored draw; the backlog (outstanding draws), each with its R3 10.5 status `OUTCOME_AVAILABLE` or `OUTCOME_PENDING`; any **open future target** (a freeze line whose draw has not been accepted: `OPEN`); the next target, its derived date and its deadline; the number of active variants and any variant that joined or left the roster since the last session; the effective class each outstanding target's records will receive (Appendix I); and any diagnostic records under the diagnostic root (unofficial, 3.4). ### 6.3 One target at a time, in MH-1's order, across weeks and interruptions (EX_125 B02; EX_127 B01, B02)

**Scope.** The weekly scope for a game is every draw from `holdout_last + 1` onward. The holdout draws are Mode H's: a method released later never forecasts them in the weekly session (they are training history for it; its forecasts on the holdout draws, if the owner ever wants them, are a development batch under a separately reviewed extension, roadmap 21b).

**Closed, under the roster of the freeze line (EX_127 B02).** A target N with a freeze line is **closed** when every record the line names is scored (or is a failure record). The line's roster is the writing session's roster plus every variant with an earlier session's ticketed DONE record for N (Terms), fixed for ever; **the current session's roster never reopens a closed target**. So: a variant released after N was frozen does not make N unclosed; it joins the session roster at its next session and its first weekly target is the first target frozen after its release; its history over earlier post-holdout draws, if wanted, is a separately identified development batch (roadmap 21b), never an edit of an old freeze line. A variant retired after N was frozen but before N was scored stays in N's line and is scored for N; it receives no new forecast because it is not in later session rosters. A revision change (E_1 revision 3, or any later one) is the same case: the new revision is a new roster member; the old revision's records stand.

**MH-1 as read here.** MH-1 lists the catch-up, then the scoring of the open prospective forecast, then the next freeze; an open forecast whose result has arrived is the lowest unclosed draw with a result, so in strict draw order it is scored first; the order below is that reading, which is also what EX_125 B02 asks for.

**Across weeks (EX_127 B01).** A freeze line made in session S1 at master version v is scored, in the ordinary case, by a later session S2 at version v' >= v, once N's result is in the master: **a score binds to the freeze line and its records, which keep their S1 binding and their v training pin; the scoring session S2 and the outcome pin v' are recorded as the score's provenance.** The scorer verifies, before reading the outcome: for each record the line names, the session record of the session that produced it (the line records each record's session id and that session record's digest, and the writing session's id) exists with that digest, and the record has a DONE ticket in that session's attempts ledger and the digest the line records; v is a verified prefix of v' (3.2 rule 2); and N `<= last_draw(v')`. Nothing in that verification requires the records' pin to equal S2's; the equal-pin rule of 3.4(a) is for **new publications** only.

**The loop.** The orchestrator alternates the forecasting half's `next` and the scoring half's `score`, and the forecasting half **enforces the order itself**, so a faulty orchestrator cannot skip a step. First `next` checks that the current ledger last row equals the session's pin; if not it exits `STALE` (every further publication in this session would refuse anyway, 3.4(a)): the orchestrator closes the session and the owner starts a new one, which continues from the same records (the game-wide DONE-ticket rule below means no pair is run twice). Otherwise `next --game G --session S` finds the lowest target N `> holdout_last` that has an accepted result and is not closed, then does one of three things:

- **N has a freeze line already** (an open forecast whose result has arrived, from this or any earlier session; or a resume after a crash between freezing and scoring): it exits `FROZE N` at once and runs nothing.
- **N has no freeze line:** first, for every open ticket for N in any session's ledger, it writes the DONE ticket if the run folder proves a completed run (a crash between publication and the DONE ticket) and marks it `FAILED_TO_START` otherwise; then for each variant in **this session's roster** without a ticketed DONE record for N **in any attempts ledger of the game** (this session's, a resumed session's, or an earlier session that ended `STALE` or whose lock was cleared), it writes an open ticket and runs one contract run in the mode of 6.4 (a failed run is DONE with `PREDICTION_FAILED` and is not run again); then, when every variant of the line roster (this session's roster plus every variant with an earlier DONE ticket for N) has a ticketed DONE record, it appends N's freeze line (6.5), naming for each variant its one ticketed DONE record with that record's own session binding (a line may name records of several sessions; it lists their session ids), and exits `FROZE N`. A set left incomplete by an interrupted session is completed by the resumed session under the same id in the ordinary case, and by a later session only where the earlier one ended cleanly without a line; in every case the earlier records are named, never orphaned and never re-run (EX_127 B01).
- **No such N exists:** the next-draw cases below.

It never looks at N + 1 while an unclosed N with an accepted result exists. After `FROZE N` the orchestrator runs `score --game G --session S --target N`: the scoring half performs the cross-week verification above, scores every record the line names that has no score line yet (6.6), and exits; then `next` runs again.

**The next-draw cases (EX_127 B01 counterexample 3).** When no accepted draw `> holdout_last` is unclosed, let M = `last_draw(v) + 1`:
- **M already has a freeze line** (the forecast is open and its draw has not happened): `next` exits `OPEN M` and runs nothing; a second set for M is never made, in this or any later session, until M's result is accepted (and then M is scored, never re-forecast).
- **M has a `SET_STARTED` ticket (any session) and no freeze line** (a set interrupted before its line): the set is completed, whatever the clock says now, for every variant of the roster of the session that wrote `SET_STARTED` without a DONE ticket for M (which is also the current session's roster: rosters change only by an install, and an install refuses while this set is unfinished; Terms, 4.3; EX_129 C01), each record classified by its own `frozen_at_utc` (6.4); then M's freeze line; exit `FROZE_NEXT M`.
- **M has no freeze line, no `SET_STARTED` ticket, and at least one hour remains before M's deadline:** `next` writes the `SET_STARTED` ticket for M (target, mode, time: the one judgement of the hour rule, persisted), runs the `FINAL_NEXT_DRAW` set for M (6.4), ticketed, then M's freeze line; exit `FROZE_NEXT M`.
- **Otherwise** (no set started and fewer than sixty minutes remain, or the deadline has passed and M's result is not yet accepted): `NONE`; the status block says M will be caught up once its result is accepted.
In every case the orchestrator then runs `close-session`, prints the status block and stops.

**Persistence and resume.** Every step is persisted in create-only records before the next begins (the tickets, the run records, the freeze line, the score lines), so a crash anywhere resumes by rerunning the command, which resumes the same session (6.1): `next` re-derives the state from the records and continues at the same N; a crash during the runs for N resumes with the line-roster variants that have no DONE ticket, after the crashed run's open ticket is marked `FAILED_TO_START`; a crash after the freeze line and before the score returns `FROZE N` without running anything; a crash during `score` resumes with the unscored records only; nothing accepted is rewritten; nothing is scored twice (6.6). - N's result is accepted and the release date is not before N's draw date: run mode `REAL_DEVELOPMENT`, tier `DEVELOPMENT_WF_EXPLORATORY` (MH-1: "ordinary walk-forward development evidence"), bound and ticketed to the session, target above `holdout_last` (3.4); these runs go to the development run root;
- M = `last_draw(v) + 1` (the gate of 3.4(a) allows `FINAL_NEXT_DRAW` for no other target) and at least one hour remains before M's deadline **when the set starts**: run mode `FINAL_NEXT_DRAW`, E2R-R41's reserved row `(WF_FORECAST, PROSPECTIVE)` unreserved as written (E2R-R44 amended; the row opens for a ticketed request bound to a session, with the developed record); the forecast is left open. The hour rule is judged once, when the `SET_STARTED` ticket is written (6.3); a set interrupted and resumed later is completed under that ticket while M's result is not accepted, each record carrying its own `frozen_at_utc` (a record frozen after the deadline is `LATE_PRE_DRAW`, below); once M's result is accepted, the variants still without a record get `CATCH_UP` records and the freeze line marks them `MISSING_BATCH`;
- no set has started and less than one hour remains, or the deadline has passed: the forecasting half refuses to start a set (`NONE`) and the status block says the draw will be caught up once its result is accepted (the owner's accepted position: a missed deadline costs that week's pre-draw standing, nothing else).
Exposure: Powerball 1587 and 1588 carry the exposure flag (5.4) in their score records and in the ledger whatever their label. Run root for `CATCH_UP` and `FINAL_NEXT_DRAW`: `results/real/weekly/contract_runs/`; its `.gitignore` lines (the run folders and the session attempts ledgers) are MHUP-B members; the forecast, witness and score ledgers and the session records are tracked, so a push of them is a witness.

**The deadline (Q4):** 00:00 local time on the draw's date, computed from the PC's clock and time zone (no new dependency), recorded with every record as the UTC instant and the local offset; the local clock is not an independent witness (6.5). Alternative, for the owner: a fixed UTC instant (12:00 UTC on the day before), independent of the PC's time zone setting.

**Effective class (EX_125 B05; the total rule is Appendix I):** a record's tier is immutable (fixed by its run mode). Its **effective class**, used by every report, league table and N1 input, is derived per record: a `FINAL_NEXT_DRAW` record whose own publication receipt time (`frozen_at_utc`) is before M's deadline is `PROSPECTIVE`; one frozen after the deadline and before M's result was accepted (a run started before 23:00 still running at midnight, or a set completed under its `SET_STARTED` ticket after an interruption; whether it was frozen before the draw itself is not established, only before the result was accepted) is **`LATE_PRE_DRAW`**, a named operational category shown in the operational portfolio view, scored and kept, never counted as prospective or catch-up evidence and never excluded from the portfolio count; it is never re-forecast (M closes when scored). A straddling set therefore classifies record by record; the freeze line summarises (`deadline_met` true only if every `FINAL_NEXT_DRAW` record of the line is before the deadline). `MISSING_BATCH` (R3 10.5) is recorded on N's freeze line for exactly those roster variants that were released before N's draw date yet have no `FINAL_NEXT_DRAW` record for N (a scheduled prospective freeze was missed); a method's back-history before its release is never `MISSING_BATCH` (EX_125 C08). **In plain words, one invented week:** Oz Lotto 1712 is next; the session starts at 22:30 on the Monday, with the hour rule met; 38 variants freeze by 23:40 and are PROSPECTIVE; one variant's run is slow and freezes at 00:05 on the Tuesday, so its record is `LATE_PRE_DRAW`, kept and shown but not counted as prospective; one variant failed, so its record is `PREDICTION_FAILED` and counts as missing. Had the owner started the session on Tuesday morning instead, no set would start, and after the draw all 40 would be CATCH-UP with `MISSING_BATCH` on the line. Had he run the command again on Monday at 23:50, `next` would have found 1712's line open and exited `OPEN 1712`, making nothing.

**Invariant (a postcondition of a completed session):** at most one open forecast per variant per game; exactly one for every variant of the open line's line roster when the session ended `FROZE_NEXT` or `OPEN`, and none for a session-roster variant absent from that line; a newly released revision has none until its first weekly target is frozen; a retired one has none after its last frozen line is scored.

### 6.5 The forecast ledger and the witness ledger: the timing proof (OFF-1; EX_125 B03; EX_127 C04)

- **Write discipline for every JSONL ledger** (attempts, forecast, witness, score): one `write` of the whole line with its newline, `flush`, `fsync` (the updater's own ledger discipline, `results_master_v0_1.py` lines 278-288); a reader that finds a final line without its newline (a crash mid-append) ignores it and reports it, and the next writer, before appending, truncates the file to the end of its last complete line and copies the fragment, value-free, to a side file beside the ledger as evidence, then appends the event; nothing is edited by hand. "Create-only line" below means a line appended under that discipline whose event is never repeated once its newline is on disk.
- A local, create-only, digest-chained **forecast ledger** per game, `results/real/weekly/<GAME>/FORECAST_LEDGER_V1.jsonl`. When every roster variant has a ticketed DONE record for target N, the forecasting half appends one **freeze line**: the target and its derived date, the writing session's id and, per named record, its session id and that session record's digest, the freeze time (UTC and local offset), the deadline and `deadline_met`, `prospective_status` where 6.4 sets it, the roster with every record's full identity (6.6), ticket and digest, each record's run mode, training pin and `frozen_at_utc`, each failed variant marked `PREDICTION_FAILED`, each `MISSING_BATCH` variant, every registered but non-runnable method by status (R3 10.3), the environment digest, and the previous line's digest. A line is appended only after every record it names is DONE; the freeze-before-outcome rule (5.3) reads this line. **The line carries no witness or publication status.**
- **What the chain proves:** that the records agree with each other; comparing it with an earlier trusted digest, kept separately, reveals later changes; by itself it proves neither when the records were made nor that the whole chain was never replaced.
- **The witness ledger** (append-only, `WITNESS_LEDGER_V1.jsonl`), the **witness evidence and verification history**, with two kinds of line, both written by `Method_Weekly_Score.py`:
  - `WITNESS_RECORDED` (`witness`): the owner, after pushing the ledgers or emailing a line's digest, records `--target N --kind github|email --ref <commit id or message id>`; the line holds the freeze line's digest, the kind, the reference, and the time recorded. It is the owner's claim, not proof.
  - `WITNESS_VERIFIED` (`verify`): the person who has checked the reference records `--target N --verified-by <role> --received-utc <instant> --evidence <text>`, where `<role>` is `project-owner` or `reviewer` (never a name: the ledger is tracked and may be pushed) and the `--evidence` text is the service's own receipt, quoted: for email, the recipient server's `Received:` header line with its timestamp and the message id; for GitHub, the `created_at` of the `PushEvent` from GitHub's public events API (`/repos/<owner>/<repo>/events`, public repositories only, retained about ninety days, and GitHub documents a delay of up to some hours before an event appears) with the pushed commit id, or an equivalent service-side event record. The tool checks what a tool can check: that the evidence text is non-empty and contains the `WITNESS_RECORDED` line's reference (the commit id or the message id); that the referenced commit or message carries the freeze line's digest is the **verifier's human check**, and the line says so (`digest_binding: human-checked`). **A commit's author or committer timestamp is not evidence**: it is set by the local clock (EX_127 C04). The verification is a human act outside the repository; the line records which role, how and when.
  - **Publication status is derived at report time, never stored in a score line or a frozen record:** `PUBLISHED_BEFORE_DRAW` when a `WITNESS_VERIFIED` line exists whose received instant is before N's deadline; otherwise `TIMELINESS_UNVERIFIED` (with "witness recorded, not verified" or "no witness" shown). A later verification changes the next report, never an accepted score: no rescoring, no edit (the three-way split holds). A witness line for an unknown freeze digest, or a `WITNESS_VERIFIED` line whose received instant is after the deadline, is kept and shown and never promotes the status. Witness status never changes a record's effective class (a `LATE_PRE_DRAW` or `CATCH_UP` record stays what it is). No routine run touches the network.
- **R3 10.5's statuses, where each lives:** `OUTCOME_PENDING` / `OUTCOME_AVAILABLE` and `OPEN` in the status block; `MISSING_BATCH` and `PREDICTION_FAILED` in freeze lines (6.4, 6.3); `PUBLISHED_BEFORE_DRAW` / `TIMELINESS_UNVERIFIED` derived at report time from the witness ledger. Appendix G is the witness lifecycle.
- **Tests (R3-D20's "must be tested"):** a ledger line edited, removed or reordered breaks the chain; the forecasting half refuses to freeze a `FINAL_NEXT_DRAW` set after its deadline, and within the hour before it; the scoring half refuses a target with no freeze line; a straddling set is classified record by record; a witness line for an unknown digest is refused; a `verify` without evidence text, or with evidence that lacks the reference, or with a name instead of a role, is refused; a verification received after the deadline does not promote; a verification added after the score changes the next report and no score byte.
- **R3 clauses superseded for this project, on ratification:** 1.3 ("freeze and push the full batch remotely before the actual target event"); 1.5's "externally verifiable pre-draw proof" (made optional); 10.1(6) ("pushed to the declared remote"); 10.2's "COMMIT AND PUSH TO REMOTE BEFORE DRAW" and "SAVE REMOTE REVISION/PUSH EVIDENCE" steps and its paragraph after the diagram ("archive remote ref/commit IDs"); 11.5 item 4's "remote publication evidence"; 17.3.9's `PROSPECTIVE` definition ("frozen and published before their draws" becomes "frozen before their deadline and recorded in the local forecast ledger; publication status derived separately from the witness ledger"); and R3-D20's "GitHub push evidence required". R3 10.5's statuses and E2R-R40C's "labelled unverified and counted" are applied as written (Appendix K).

### 6.6 Scores and the league table (EFF-1; EX_125 C04, C09; EX_127 C02)

- A local, append-only **score ledger** per game, `SCORE_LEDGER_V1.jsonl`: one line per scored record. **Two identities, kept apart (EX_127 C02):** the **scientific identity** `(game, method, method revision, variant, target, the scored record's digest, scoring policy id)` is the duplicate guard: one routine score line per scientific identity, whatever the execution's score run id, and a second routine attempt for the same identity refuses (a planned negative test runs the scorer twice with different score run ids); the **execution provenance** `(score run id, scorer version, scoring session, outcome pin)` is recorded on the line and is not part of the guard. The scoring policy id names the ratified measure set and formulas; a corrective or new-measure scoring carries a different policy id and an `amendment_of` field naming the accepted line it stands beside, never over. The line holds the per-target quantities WF-1B already computes (TOP and WORST matches, Powerball match, prize division, rank positions), the scored record's digest (or the failure record's), the forecast's training pin and the outcome's pin (the master version and SHA-256 that supplied it: R3 11.5's **outcome record**, which answers finding A11), the tier, `frozen_at_utc`, the effective class (Appendix I), any exposure flag. Report grouping keys are (game, method, revision, variant) and the effective class. This ledger is R3 11.5 item 6, the **evaluation record**. The scoring code reuses WF-1B's measure functions through a thin per-target driver; no measure, label or formula changes. Each method revision is reported separately (R3 6.3).
- The weekly path reads only the new runs and the new draw. The league table is built from the score ledger, cumulative, with PROSPECTIVE, CATCH-UP and development evidence in separate columns, `LATE_PRE_DRAW` in the operational portfolio view only, the number of draws and the exposure period beside every figure (a variant released later has fewer draws, shown, never hidden), and Mode H and the development reports referenced in their own columns; nothing is retuned because of its ranking (MH-1). N1 and the significance tables run over the PROSPECTIVE and CATCH-UP records only, with their own family definitions, counts and multiple-comparison allowance, in the full report; cohorts of different exposure are compared on matched draws.
- **Cadence (Q6):** each session prints a short after-draw note and writes the dated cumulative table, with a search-log row of type `WEEKLY_TABLE` (C09: every dated table is logged); the full report with N1 on request or monthly, each a new dated report with its own search-log row of type `WEEKLY_REPORT`; earlier reports stay as published.
- **Retired revisions:** their forecasts and scores stay where they are; the league table shows "as published" and "current methods" side by side (D-8); a retired index is a later small item (roadmap 21b), not part of this design.

## Appendix F. The weekly session: states and event order (acceptance item 2; EX_127 B01, B02)

One owner command, two processes, one target at a time. Persisted state, all create-only: the session record and lock, the attempts ledger (tickets), the run records, the freeze lines, the score lines. The orchestrator holds no state of its own.

```
Run_Weekly_Session.bat --game G
  -> orchestrator (imports neither side)
     1. Run_Experiment.bat Method_Weekly_Forecast.py status --game G           [prints the status block]
     2. if ACTIVE_SESSION.lock exists:
             .venv\Scripts\python.exe -I src\package_tools\process_check.py check-no-runs --game G   [acts on no process]
               CLEAN -> resume token RESUME_<S>_<time>.json (create-only); otherwise the orchestrator stops here
             Run_Experiment.bat Method_Weekly_Forecast.py open-session --game G --resume
               requires an unused resume token for the session S the lock names; records it as a RESUMED ticket
               reopens S (same id, same pin, same roster); refuses otherwise, and if the updater lock exists,
               or if the closure/environment digest differs from S's record
        else:
             Run_Experiment.bat Method_Weekly_Forecast.py open-session --game G
               refuses if the updater lock exists
               SESSION_<S>.json create-only (pin = ledger last row; roster = released, unretired variants;
               closure and environment digests); lock written
     3. loop:
          Run_Experiment.bat Method_Weekly_Forecast.py next --game G --session S
            if ledger last row != S's pin: -> STALE, stop                   (owner opens a new session; records kept)
            N := lowest target > holdout_last with an accepted result that is not closed under its LINE roster
                 (no freeze line yet, or a line with an unscored record)
            if N exists:
               if N has a freeze line: -> FROZE N                         (open forecast with a result now; or resume)
               else: mark FAILED_TO_START every open ticket for N (any session) whose run never completed
                     for each variant of S's roster without a DONE ticket for N in ANY session's ledger:
                        open ticket -> one run (mode by 6.4) -> DONE ticket (PREDICTION_FAILED is DONE)
                     when all DONE: freeze line for N, line roster = S's roster + variants with earlier DONE tickets,
                        one ticketed record each, each with its own session binding -> FROZE N
            else: M := last_draw(pin) + 1
               if M has a freeze line: -> OPEN M, stop                      (nothing made; never a second set)
               elif M has a SET_STARTED ticket (any session): complete the set (as above, FINAL_NEXT_DRAW,
                        each record by its own frozen_at_utc), freeze line for M -> FROZE_NEXT M, stop
               elif >= 60 min before M's deadline: SET_STARTED ticket for M (the one judgement, persisted);
                        ticketed FINAL_NEXT_DRAW set for M, freeze line for M -> FROZE_NEXT M, stop
               else -> NONE, stop                                           (caught up once M's result is accepted)
          Run_Evaluation.bat Method_Weekly_Score.py score --game G --session S --target N
            cross-session check: per named record, its own session record + digest and its DONE ticket + digest;
                                 line pin v is a verified prefix of the current version v'; N <= last_draw(v')
            outcome_release_allowed(G, N)
            for each named record without a score line: read N's outcome once, score, append (create-only;
                                 provenance: S, v'; binding and training pin v unchanged)
          (back to next)
     4. close-session: lock removed on FROZE_NEXT / OPEN / NONE / STALE; left on a non-zero child exit
     5. print the status block; exit
```

Properties: (i) `next` never considers N + 1 while an N with an accepted result is not closed under its line roster, so N is closed before N + 1 whatever the orchestrator does; (ii) a crash after the freeze line and before the score resumes (same session id) at `next`, which returns `FROZE N` without running anything, then `score` runs; a crash during the runs for N resumes with the line-roster variants that have no DONE ticket, after the crashed run's open ticket is marked `FAILED_TO_START`; a crash during `score` resumes with the unscored records only; (iii) no accepted record is rewritten at any step, and no freeze line is edited by a later roster; (iv) an open `FINAL_NEXT_DRAW` forecast whose result has now arrived is the lowest unclosed N with an accepted result, so it is scored before anything else, in whatever session, with both pins recorded; (v) an unaccepted draw stops the loop (`OPEN` or `NONE`); the next session continues from it; a set interrupted and left without a line by `STALE` or a cleared lock is completed by the next session from the game-wide DONE tickets, never re-run; (vi) a rerun before M's result makes nothing (`OPEN M`); (vii) a variant released after N's line was written is not in N's line roster, so N is closed without it and the newcomer's first target is the first line written after its release; a variant retired after N's line is written stays in N's line and is scored for N.

**The lock and session transitions:** no lock -> `open-session` writes the record and the lock -> the loop -> `close-session` removes the lock (clean end) | the process dies (lock stays, record stays, tickets show the open run) -> the next `Run_Weekly_Session.bat` runs `check-no-runs`: `CLEAN` -> resume token -> `open-session --resume` under the same id -> the loop continues from the records; not `CLEAN` -> nothing runs until the process has ended (the owner closes its console or waits) and a later check is `CLEAN`. `clear-session-lock` (the lock removed without resuming, for a session the owner does not wish to continue) is also allowed only on `CLEAN`, writes a clearance record, and leaves every record and ticket of the old session in place; the next session scores its lines by the cross-session rule and completes any incomplete set from the game-wide DONE tickets: it runs only the variants without a DONE ticket for that target and writes the line naming the old session's records with their own binding, so nothing is adopted, discarded, orphaned or re-run (6.3).

## Appendix G. The witness lifecycle (acceptance item 3; EX_127 C04)

```
freeze line for N appended (digest d)                      [forecast ledger; local; the fact]
   |
   |-- optional: owner pushes the ledgers / emails d        [outside the repository]
   |-- optional: owner records WITNESS_RECORDED(N, kind, ref, time recorded)   [witness ledger; a claim]
   |-- optional, any time later: the verifier (a role, never a name) checks the reference and records
   |      WITNESS_VERIFIED(N, verified-by, received-utc, evidence text)         [witness ledger; evidence]
   |      refused unless the evidence text contains the reference; the digest binding is the verifier's human check
   |
score for N appended (facts only: quantities, pins, tier, frozen_at_utc, effective class)   [score ledger]
   |
report (any date): publication status derived now:
     PUBLISHED_BEFORE_DRAW  if a WITNESS_VERIFIED line for d has received-utc < N's deadline
     TIMELINESS_UNVERIFIED  otherwise, shown as "witness recorded, not verified" or "no witness"
```

**What counts as evidence (EX_127 C04):** the service's own record of receipt, quoted in the `--evidence` text: for GitHub, the `created_at` of the `PushEvent` that carries the pushed commit id, from GitHub's public events API (`/repos/<owner>/<repo>/events`: public repositories only, retained about ninety days, and GitHub documents a delay of up to some hours before an event appears, so the verifier must look inside that window), or an equivalent service-side event or webhook delivery record; for email, the recipient server's `Received:` header line with its timestamp and the message id. The event carries the commit id, not the freeze digest; that the commit's ledger file (or the message body) carries the digest d is the verifier's own check, which the line records as `digest_binding: human-checked`; the tool checks only that the evidence text is present and contains the reference. **A commit's author or committer timestamp is set by the local clock and is not evidence.** A `received-utc` typed without such a text is refused. The verification is a human act outside the repository; the line records which role (`project-owner` or `reviewer`, never a name), how and when.

Worked cases (invented): (1) score first on 15 November, the owner pushes on 16 November and records the witness; the reviewer fetches the repository's events on 20 November, finds the `PushEvent` carrying that commit id with `created_at` 16 November 09:12 UTC, before the deadline, checks the commit's ledger file for d, and records `WITNESS_VERIFIED` with that event quoted: the report of 21 November says PUBLISHED_BEFORE_DRAW; the score line of 15 November is byte-identical. (2) A `WITNESS_RECORDED` line names a commit that does not exist: the verifier records nothing; status stays TIMELINESS_UNVERIFIED, the claim is shown. (3) A commit exists but carries a different digest: `WITNESS_VERIFIED` is not written (the verifier found no match). (4) A push received after the deadline: `WITNESS_VERIFIED` with received-utc after the deadline is recorded and shown; the status does not promote. (5) The ninety days have passed and no event is retrievable: the verifier has nothing to quote; status stays unverified, which is the honest answer. (6) A `LATE_PRE_DRAW` record with a verified witness stays `LATE_PRE_DRAW`: witness status never changes an effective class. No step needs the network inside the project's tools; verification is a human act recorded afterwards.

The coordinator's orphan marker is never touched, the identity, creation-time and ancestry checks of 6.1 are unchanged, and no barrier is removed silently. The process tool already specified is enough: the install check of this appendix is the fresh check.
