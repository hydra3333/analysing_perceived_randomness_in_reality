## Part 2. Findings

### Q1. CORRECTION - the roster can still change under an unfinished set: the release record is written after U is released
**Where:** Appendix J steps 14-16 (lines 727-729); Terms, Roster (line 22); 4.3 (line 166); B.3 C01 row.
**Text:** step 14 "Delete **E**, then **P**, then release **U**"; step 15 "The record tool writes the **release record**"; Terms "so every session that touches an unfinished set has the same roster as the session that started it".
**What is wrong:** the session roster is computed at `open-session` "from the release records minus the retired entries" (4.3). The only thing stopping `open-session` during an install is U (6.1). U is released at step 14, but the release record (the roster change) is written at step 15 and committed at step 16. Between them, and for the whole of a STOP at step 15 or 16 ("re-create P ... after the fix"), a weekly session can open under the old roster, write `SET_STARTED M` (or start a catch-up set) and be interrupted; the release record then changes the roster under that unfinished set. The step 2 check is never repeated after step 2. This is the EX_129 C01 case again, through the normal install path.
**Smallest fix:** release U last, after step 16 (step 14 deletes E and P only; a new final step releases U), and make the release-record tool refuse while any session lock exists or any unfinished set exists. 4.3's "after the barriers are removed" becomes "after E and P are removed".

### Q2. CORRECTION - the repeated checks at steps 6, 10 and 13 contradict U
**Where:** Appendix J steps 2, 6, 10, 13 (lines 715, 719, 723, 726).
**Text:** step 2 "must print `CLEAN`: no project process ...; no `ACTIVE_SESSION.lock` for either game; no updater lock; no target ... with a ticket but no freeze line"; step 6 "The no-active-run check, after the gate copy (`CLEAN`)"; steps 10 and 13 "The check repeated (`CLEAN`)".
**What is wrong:** if "the check" is the step 2 preflight, it can never be `CLEAN` from step 3 to step 14, because the install itself holds the updater lock. If it is only the process listing of 6.1 (`check-no-runs` lists processes; the lock and ticket conditions appear only in step 2), then a session lock or an unfinished set created between steps 2 and 3 (before U exists) is never caught. The text does not say which.
**Smallest fix:** define the repeated check as the full step 2 preflight with one stated exception: an updater lock whose content is exactly `INSTALL <this package> <utc>` is expected; give it a command form (for example `check-no-runs --install <package>`) and add it to L-I1.

### Q3. CORRECTION - the program that takes and releases U is not named
**Where:** Appendix J barriers paragraph (line 701), steps 3 and 14; section 8 ("the install tool's holding of the updater lock"); Appendix K new names (line 760); step 1.
**Text:** "taken by the install tool with the updater's own create-exclusive open"; step 14 "the tool deletes the lock only if its content names this install"; step 1 "includes the SHA-256 of the package's `process_check.py`".
**What is wrong:** no file or command is named. For MHUP-A the tool is not installed at step 3, yet PRE verifies only `process_check.py` from staging. `process_check.py`'s command list (6.1, K) has no take/release command. Rulebook rule 7 and the deny patterns cannot list an unnamed tool.
**Smallest fix:** name the command (for example `process_check.py take-install-lock --package P` and `release-install-lock --package P`), say it runs from staging for MHUP-A after PRE verifies its SHA-256, and add it to K and to the rulebook/deny-pattern list.

### Q4. CORRECTION - "a ticket but no freeze line" also matches Mode H tickets, which never get a freeze line
**Where:** Appendix J step 2 and "No forecast set may be unfinished" (lines 711, 715); Terms (22); 4.3 (166); L-R6.
**Text:** "the preflight refuses while any target of either game has a ticket but no freeze line (read from the attempts ledgers and the forecast ledgers, value-free)".
**What is wrong:** Mode H writes open and DONE tickets for every holdout pair in "the batch's attempts ledger" (5.1), and holdout targets are scored from `BATCH_COMPLETE` and the plan roster, not from a freeze line (5.3: freeze lines are "for a later target"). Read as written, every install after the Mode H batch is refused for ever, including MHUP-B in the "after the Mode H score is sealed" option of 4.4 step 1.
**Smallest fix:** say "any target above `holdout_last` with a ticket in a weekly session's attempts ledger and no freeze line in that game's forecast ledger"; Mode H and WF-1A attempts ledgers are not read. Add a Mode-H-tickets-present case to L-R6.

### Q5. CORRECTION - the "finish the set first" rule can deadlock, and the text says it cannot
**Where:** 4.3 (line 166); Appendix J (line 711).
**Text:** "the owner finishes the set by running the weekly session, which always completes it (6.3)".
**What is wrong:** 6.3 completes the set only if the installed session code works. If a set is left unfinished because of a defect in `Method_Weekly_Forecast.py`, the orchestrator, a launcher or a gate, the fix is a package; the package's install is refused while the set is unfinished; the set cannot be finished without the fix. No exit is defined, so the game is blocked. The C01 hazard is only a roster change, so the rule is wider than it needs to be.
**Smallest fix:** refuse only a package whose release record names entries or which retires a variant (a roster-changing package) while a set is unfinished. A non-roster package (MHUP-B-style empty release record, a bug fix) may install. State this in 4.3 and Appendix J, and add the non-roster case to L-R6. Otherwise state the deadlock and the owner-approved exception route.

### Q6. CORRECTION - the never-existing byte-code folder is created by a nested launch; `-I` children bypass the rule
**Where:** 4.1 Byte-code (line 146); 6.1 (`Run_Evaluation.bat`, `Run_Weekly_Session.bat`, process tool with `-I`); Appendix H byte-code row (line 664); B.3 C02; L-U3.
**Text:** "`-B` stops it writing there, so the folder is never created ... the same path suits a nested launch ... because the variable is set inside the launcher's `SETLOCAL`"; "`Run_Evaluation.bat` and `Run_Weekly_Session.bat` are written with the same three"; "every Mode H and weekly command runs Python with `-B` and with `PYTHONPYCACHEPREFIX`".
**What is wrong:** (i) `Run_Weekly_Session.bat` sets the variable, so the orchestrator's environment carries it, and `Popen` passes it to each `Run_Experiment.bat` / `Run_Evaluation.bat` child. Each child's venv probe, `"%PY%" -c "import sys,pathlib;..."` (`Run_Experiment.bat` line 31 at `3a9f6ac`, before change (a)), runs **without** `-B` and **with** the inherited prefix, so it writes byte-code under the prefix and creates the folder (reproduced: CPython 3.13 wrote `fnmatch`, `re/*` and `_distutils_hack` byte-code under the prefix). Change (b) then refuses that child and every later launch until someone deletes the folder by hand. So the first weekly session fails at its first child, and "never created" is false. The coordinator path is not affected, because `Run_Coordinator.bat` does not set the variable. (ii) The orchestrator runs the process tool "with the venv's Python and `-I`". `-I` implies `-E`, which ignores `PYTHONPYCACHEPREFIX` (and `PYTHONDONTWRITEBYTECODE`). With no `-B` either, that weekly child reads `__pycache__` beside its sources (reproduced: the sentinel was imported under `-I -B` with the prefix set). (iii) The Linux import test in L-U3 does not cover either case.
**Smallest fix:** add `set "PYTHONDONTWRITEBYTECODE=1"` to each launcher before its venv probe. It is inherited by every nested Python, including the probe, so the folder stays absent. Or have the orchestrator remove `PYTHONPYCACHEPREFIX` from its children's environment. Run the process tool with `-I -B -X pycache_prefix=<the folder>`, or exclude it from the claim by name. Add an L-U3 case: launcher started with the variable already set, probe included, folder still absent. The T017 rehearsal should check this on Windows. Change "exactly three changes" accordingly.

The current wording, "from `v_f`'s last draw + 1 through at least `holdout_last`", is ambiguous for fixtures whose master already passes `holdout_last`.

### Q8. CORRECTION - the updater's own refusal tells the owner to delete U by hand

### Q9. CORRECTION - D3 understates what the unbarred programs write, and misses the WF-1A driver
