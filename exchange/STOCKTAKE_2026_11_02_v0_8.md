## (a) Mode H, the one-time holdout test

**What it is (DECIDED: R3 sections 6 and 10; register v0.23 "Terms for that design").** Every released variant forecasts each of the ten holdout draws of a game, each forecast using only the draws before its target. The forecasts are frozen, then the ten draws are scored once with the same scorer and measures as the development reports.

**What is frozen before any holdout result is read (PROPOSED, EX_123 section 1, Reading A; OPEN until you decide Q1).** The register's wording says "all frozen before the holdout is opened" and also "walk-forward". Both cannot hold literally: the forecast for Powerball 1578 must train on draw 1577, which is itself in the holdout. My recommended reading: open the holdout and add the results first; then run the Mode H batch, where each method still sees only the draws before its own target (the N-1 rule, which test T-05 proves); then, and only then, let the scorer read any holdout result. The alternative (release one result at a time, forecast, score, repeat) is possible but needs a new step engine and more review.

**Frozen before opening, in any reading (PROPOSED, EX_123 section 3.1):** the study plan: which variants, which measures, which seed, the exact code and the exact list of installed packages (R3-T50, which forbids any software upgrade inside Mode H).

**Kept to one run (PROPOSED, EX_123 sections 4.2-4.4):** one Mode H batch per study plan per game; a second plan is refused. One scoring attempt; a second is refused unless the first stopped before reading any result. Every record is create-only (the file system refuses to overwrite), as all frozen records are today (BUILT).

**Flagged draws (DECIDED: HX-1 and HX-2, exposure record v0.3).** The record's item 1 says a reviewer chat displayed Powerball 1585-1588 on 25 October 2026. Of those, 1585 and 1586 are inside the holdout: they carry a flag in Mode H's records and report. 1587 and 1588 are after the holdout: they carry the same flag when the weekly catch-up scores them. Item 5 notes that ratified documents quote draw 1587 as drawn-order evidence; it gets no Mode H flag because it is outside the holdout. **Why flagged draws still count:** the flag records that a reviewer saw those results; no method was changed because of them, so the forecasts are not tainted, and leaving draws out would make the result less honest, not more (your rule: mark, never suppress). The flag is information; it changes no score.

**What Mode H can and cannot show.** Ten draws per game is a small test. It can catch a method that was secretly tuned to the development draws (it would collapse on fresh ones) and it gives the first honest fresh-draw numbers. It cannot show a small real effect; with ten draws almost any method looks consistent with chance. The real test is the weeks that follow. **Afterwards (PROPOSED, EX_123 Q7; OPEN):** the ten draws become ordinary history for training and scoring, like any other past draw.

## (b) Re-training, and keeping old results honest

**What is recalculated for each forecast (BUILT; DECIDED: R3 section 10 "Fitting", H-1 5.2 "fresh fit for every target").** Every forecast is computed from scratch from the draws before its target. No model is stored between targets. What each of today's methods looks at:
- E_1 all earlier draws (counts). E_2 all earlier gaps (or the last 8). E_6, E_7, E_9 all earlier draws, with some variants weighting older draws less. E_8 periods of 13, 26 or 52 draws. E_3, E_4 a moving window of 52 or 104 draws. E_10 a short window against a long one. E_17, E_18, E_19 all earlier draws (gaps, ages, cycles).
- Future methods: each is designed before coding, and its window is fixed in its specification (E2R-R14A). Nothing beyond today's 12 methods is designed (OPEN). Any cache or incremental fit would need a reviewed proof that it gives byte-identical forecasts (DECIDED: R3 10).

**Can anything alter an earlier frozen forecast, score or ranking? (BUILT: no.)** Forecast records are create-only and each carries a digest of its content. New results cannot change them: a forecast for draw N depends only on draws before N, and test T-05 checks that changing N or later draws leaves every forecast byte-identical. A software change to a released method is a new revision with its own identity; the old forecasts keep the old identity (DECIDED: E2R-R14A, R3 6.3). A published ranking report is a committed file; a new report is a new file. **Reproducing earlier findings:** every run record pins the results file version and digest, the method revision, the variant and the code; rerunning the same inputs gives the same bytes (BUILT and tested across Windows and Linux for the scorer).

**Re-running history (DECIDED: R3 10.4; H-1 5.2).** Allowed for debugging, for a new method revision, or for a full re-batch (which WF-1C will make faster). Every rerun gets a new run identity and is labelled RETROSPECTIVE or as development evidence; it never acquires the original's pre-draw standing, and the original stays on disk.

## (e) Changing or adding a method

**The steps (BUILT process; `doc/METHOD_TEMPLATE/README.md` draft 4).** You start it by naming the idea and its catalogue number (E_2 to E_62 are reserved names; a new idea beyond them is OPEN and needs a catalogue amendment). **Catch-up and its prospective record (DECIDED: MH-1; R3 6.3, 10.4).** A new method's history is development evidence: a full walk-forward over all past draws, including the post-holdout ones, labelled as such. Its CATCH-UP record can begin only at draws after its install date; its PROSPECTIVE record begins at its first forecast frozen before a draw. An improved version is a new revision with a new identity and starts its own record; the old revision's results stay under the old identity, so an improvement is never credited with earlier results.

**Fair comparison with different history (DECIDED: R3 6.3, 6.4; BUILT in part).** The report shows each method's results over the draws it actually forecast, with the number of draws beside every figure. Side-by-side comparison uses the common draws. Version-stratified results (one unchanged method across its draws) and the evolving-portfolio view (what the project forecast each week) are reported separately and never mixed.

## (f) What you will see

**One forecast (BUILT; invented example).** For Powerball, variant `E_6:BETA_FORGET_1Y_V1` (invented name), target 1592: a full ranking of the 35 main numbers and of the 20 Powerball numbers; TOP = the seven best main numbers plus one Powerball, say `[3, 9, 14, 22, 27, 31, 35]` with PB 8; WORST = the seven lowest plus the lowest Powerball. **Scoring (BUILT):** after the draw, how many of TOP's seven match the drawn seven (0-7), whether the Powerball matched, the same for WORST, the prize division each would have won, and the rank position of each drawn number in the method's ranking. The report compares these with the fair-draw reference (an average of 1.4 matches of seven for Powerball) and with 10,000 simulated fair-draw histories (N1).

**Where things are saved (BUILT for development; PROPOSED for the rest).** Run records under `results/real/development/` (development) and, PROPOSED, `results/real/holdout/` and `results/real/prospective/<GAME>/` with a forecast ledger and a score ledger. Reports under `results/method_rankings/`. The one search log at `results/audit/SEARCH_LOG.csv`. Results files under `source_data/`.

**The league table (DECIDED: R3 17, MH-1).** One row per variant, with its measures and the number of draws; development, Mode H, catch-up and prospective kept in separate tables or columns, never pooled; a hindsight-advantage column where in-sample figures appear. Made by the weekly command (short form) and by the full report on request (PROPOSED).

**Which numbers matter.** For a track followed for many weeks: the family-level figures (Bonferroni P and the N1 maximum P), which allow for the number of variants tried; a single variant's p-value is one of 80 and looks small by chance about once in 80. **Telling signal from fluke, over-tuning and self-made pattern (DECIDED: H-1 2A, the four origins PO-1 to PO-4):** a fluke fades on fresh draws; over-tuning shows as development results that Mode H and prospective draws do not repeat; a method's own structure shows up in the fair-draw simulator too (N1 runs the method's scoring against invented fair histories, so a pattern the method creates appears there as well). Only persistence on genuinely new draws (PO-4) counts.

**Genuinely encouraging (my view, PROPOSED as a standard, not a rule).** A predeclared track whose prospective family-level P stays below about 0.01 after allowing for every variant, and whose effect size is stable across the prospective weeks, not carried by one lucky week. **How long:** a real effect large enough to matter (say one extra match of seven every few draws) would show in roughly 50-100 prospective draws, one to two years at one draw a week per game; a small effect would take far longer. Ten holdout draws or a handful of weeks can only rule out large effects.

**How (BUILT: `src/results_master_v0_1.py`, run by `Run_Results_Updater.bat`).** Confirmed: it reads only Lotterywest's results-search page on `www.lotterywest.wa.gov.au`, with a real headless browser and two-second pauses; no other site, no API, no automation of The Lott (DECIDED: TSC-1 retires the two-site checker). Some accepted tests read the real results file through that reader, so the test suite would fail, and every install's suite step would STOP. **What does not refuse:** nothing in the project. The updater itself still works (it only checks its own ledger), and the earlier committed records remain readable as files. **The version-2 fix (PROPOSED, EX_123 section 2.2):** accept a ledger of any length whose lines chain correctly (INIT, then UPDATE or NO_CHANGE rows that agree with each other), and check a run's pinned version by hashing the first lines of the current file, which works because the updater only appends. It must be installed first because the first update makes the whole system unusable until it exists.

**Tied to the exact results version (BUILT, extended).** Every run record and every report pins the results file's version number and its SHA-256 digest; the version-2 reader keeps those pins valid after later updates, and refuses if any earlier line of the results file has changed.

**Offline (DECIDED: OFF-1).** Yes. Only the update needs the internet. Everything else runs from the PC.

### 3. The phrase "never recomputed" needs three qualifications

**First: forecasts.** A frozen forecast must not be changed or substituted. It is legitimate to run a later historical experiment with the same target and different code, but that produces a *new* separately identified retrospective record and cannot acquire the earlier forecast's timing status.

**Second: scores.** An accepted original score, scorer version and input provenance should remain immutable. Scores can nevertheless be independently verified or, if a scoring defect or new metric is found, calculated again under an explicit new scoring/analysis identity. Do not silently edit the accepted old score; show an auditable correction or supersession if needed. A blanket ban on recalculating anything would make verification and scientific correction impossible.

**Third: rankings.** A leaderboard is a *derived view* of specified frozen records under specified rules. It can and should change when new draws are scored, new methods enter, revisions retire, or the comparison cohort/time window changes. A newly generated report must show its source set, date, reporting rule and relevant version, while the old published report remains reproducible. Thus "preserve earlier published rankings" does not mean "keep the current ranking forever fixed". Dynamic ranking is exactly what the owner appears to want.

A minimal illustration: methods A and B have forecasts on draws 1-50 and a report ranks them. Method C is later introduced and backtested over 1-50. The new report may rank A, B and C over that common historical interval, clearly marked as development evidence, without changing A or B's original scores or the earlier two-method report. A historical backtest of a newly invented method does not make its results independent evidence merely because it appears beside older forecasts. # Direction for the operational procedures, v0.1

Plain English. Written by the new Claude chat on 2 November 2026 from the owner's part (d) of the stock-take
record (STOCKTAKE_2026_11_02), as amended by the previous Claude chat's Responses 3 and 3b and by the ChatGPT
reviewer's Response 2, and as the owner accepted them on 2 November 2026. It says where we are heading and how
the finished system will behave. It is a direction statement, not a specification: the design documents and the
ratification register hold the exact rules, and they prevail wherever this file is looser.

Each point is marked: (ratified) an owner decision already in the register, with its ID; (agreed 2 Nov 2026) a
position the owner accepted in the stock-take, to be carried into the Mode H design and ratified there;
(open) still to be decided.

## 1. What will be in place

- The software; the two results files (one per game, Powerball and Oz Lotto, never pooled); every method's
  forecast for every draw, in draw order, frozen when made; the score of every forecast once its draw is known;
  and the ranking reports. (ratified: R3; built for the development draws)
- The clock is the draw number within each game. Dates are used only to check incoming results and to decide
  whether a forecast was frozen before its draw. (ratified: R3 1.1)
- Every forecast for draw N is calculated fresh from the draws before N, never from a stored model. Each method
  follows its own fixed rule about how far back it looks: most look at all earlier draws, a few are defined to
  look at a window (for example the last 52 or 104 draws), because how far back to look is part of what that
  method is. (ratified: R3 10; E2R-R14A)
- After every draw, the forecasts for it are scored, and the rankings are refreshed. (ratified: R3 17)

## 2. The three kinds of record, and what may change

- **Forecasts** are frozen and never changed or replaced. A later rerun of the same target is a new record with a
  new identity and no pre-draw standing. (ratified: R3 10.3, 10.4)
- **Scores** are kept as accepted. If a scorer fault or a new measure needs it, a new scoring run is added
  beside the old one under its own identity; the old one is never edited. (agreed 2 Nov 2026)
- **Rankings** (league tables, reports) are views of the frozen records and are meant to change: when a draw is
  scored, a method added or retired, or the comparison window changed, a new dated report is made. Every old
  report stays as published. "Re-ranking" means a new report, never an edit. (agreed 2 Nov 2026; ratified in
  substance: D-8, R3 17)

## 3. Labels on every scored draw

- PROSPECTIVE: the forecast was frozen before its draw.
- CATCH-UP: made after its draw, in draw order, from the draws before it, by a method revision installed before
  that draw. Counts in the rankings, kept apart from PROSPECTIVE. (ratified: MH-1)
- Development evidence: everything else (the walk-forward over past draws, a new method's back-history, a draw
  before the method existed). Ranked in its own table. (ratified: MH-1, R3 17)
- Mode H results carry their own label. Powerball 1585, 1586 (Mode H) and 1587, 1588 (catch-up) also carry an
  exposure flag; they count fully. (ratified: HX-1, HX-2)
- Same arithmetic for all; only the label and the table differ. The label is what lets an outsider see which
  forecasts were genuinely made in advance. (agreed 2 Nov 2026)
- The exact rule for "installed before that draw" is to be settled in the design (open: Q5); the intended answer
  is a local install record, so that no Git history is needed (ratified principle: OFF-1).

## 4. Mode H, the one-time holdout test

- Every released variant forecasts each of the ten sealed holdout draws per game, each from the draws before
  its target; all forecasts are frozen; then the ten are scored once. (ratified: register v0.23 "Terms")
- The statement Mode H is meant to support, as the owner now reads it (agreed 2 Nov 2026, subject to the design
  review): "a locked holdout study: the study plan and code were frozen before the holdout was opened; every
  forecast used only draws before its target; no forecast was scored until all were frozen." This is option A.
  Option B (reveal one result at a time) stays in the design as the alternative for the reviewer to weigh.
  Option C (all ten forecasts from the development draws only) is withdrawn: every released method would give
  the same forecast ten times, so it would not test the retraining process. The register's phrase "all frozen
  before the holdout is opened" is to be amended to the wording above in the Mode H design. (open until the
  design is ratified: Q1)
- Mode H is also the dress rehearsal of the weekly process: it uses the same engine and the same guarantees.
- Ten draws can only rule out large effects; the report will say so. Afterwards the ten draws become ordinary
  history. (agreed 2 Nov 2026; Q7 open on the display rule)

## 5. The normal week

One sitting per week, both games, any day from Friday to Monday. (agreed 2 Nov 2026)

1. Run the results updater (the only step that needs the internet). It fetches from Lotterywest's results page
   only, the current month and the five before it; it refuses unless the fetched draws overlap and match the
   file it already holds, and new draws are consecutive. Always give it its arguments; run bare, it still runs
   an update. (built; TSC-1)
2. For each game, one command. It prints a status block first: last accepted draw, last forecast, last scored
   draw, backlog, next target and its deadline, number of active variants, the label each target will get.
   (agreed 2 Nov 2026)
3. The command then: catches up any draw that has a result but no forecast, one draw at a time in order
   (forecast N from the draws before N, reveal N, score N); scores the open forecast whose draw is now known;
   freezes the forecast for the next draw and appends it to the forecast ledger. Nothing is scored twice; a
   draw whose result is not yet in is left open, never skipped and never guessed. (ratified: MH-1; mechanics
   open in the design)
4. Exactly one open forecast per variant at any time, once that variant has caught up; a newly released
   revision has none until its walk-forward is done; a retired one has none ever again. (agreed 2 Nov 2026)
5. Copy source_data/ and results/ to the backup drive. Optionally push the ledgers to GitHub as an outside
   witness. (agreed 2 Nov 2026; OFF-1: the push is optional)
6. A forecast counts as PROSPECTIVE only if frozen before the deadline for its draw (proposed: midnight Adelaide
   time before the draw date; open: Q4).

## 6. Missed weeks

Any number of draws, one game or both, independently. The command walks forward over the missed draws exactly as
in step 3, and leaves the next forecast ready. A forecast made after its draw is CATCH-UP (or development
evidence), never PROSPECTIVE, however strict its isolation. (ratified: MH-1, R3 10.5)

## 7. Adding a method

- Specification (reviewed, ratified; every variant setting fixed); code package (installed non-runnable);
  release package; then it joins the cohort. (built process; template draft 4)
- It is caught up by a full walk-forward over all past draws. Today that is a new full batch of every variant
  (ratified: ER-6); WF-1C's parallel workers come before the next wave for that reason (ratified: ORD-1).
  Reusing existing frozen records instead of re-running them is an efficiency item for after WF-1C. (agreed
  2 Nov 2026)
- Then a new dated ranking report over all current methods and the draws they share. The new method's history
  is development evidence; its CATCH-UP record starts at its install; its PROSPECTIVE record starts at its first
  forecast frozen before a draw. An improved version is a new revision with a new record; it is never credited
  with the old revision's results. (ratified: R3 6.3)

## 8. Retiring a method revision

- Its code and tests are archived (built: CODE-3) and its registry entry becomes RETIRED (ratified: E2R 12A.2).
  It makes no new forecasts.
- Its frozen forecasts and scores stay where they are, because the reports point at them by path and digest. A
  "retired" folder holds an index pointing to them, not the records themselves. (agreed 2 Nov 2026)
- Reports show "as published at the time" and "current methods" side by side (ratified: D-8). A method is
  retired only when superseded, never for performing badly; poor performers stay visible (mark, never
  suppress).

## 9. Offline, timing proof and backups

- Everything installed runs without GitHub; only the updater needs the internet. (ratified: OFF-1)
- A forecast's timing rests on a local, create-only, digest-chained forecast ledger. The chain shows the records
  agree with each other and that nothing changed since it was last checked; it cannot prove the PC clock. A line
  is proved to predate a draw only when an outside witness (a GitHub push, an emailed digest) received it before
  the draw; the witness is optional and the report says whether one exists. (ratified: OFF-1; wording agreed
  2 Nov 2026)
- Backups: source_data/ and results/ after every weekly session and before every install, to a second drive,
  with one restore test; GitHub holds the code, documents, reports and the six results-file records, but not
  the git-ignored run, attempts and score records. (agreed 2 Nov 2026)

## 10. Before any of this can run

- The version-2 results reader must be installed before the updater is run in any form: even an update that
  finds nothing new writes a line that today's readers refuse. (register v0.23 probe A1; agreed 2 Nov 2026)
- Then, per game and each with the owner's separate approval: freeze the study plan and open the holdout; the
  first update; the Mode H batch; the Mode H scoring. Then the owner decides whether to declare the system
  developed (ratified: GOAL-1).
- Planning target: Mode H done and the weekly session installed by about 13-15 November 2026, so the first
  PROSPECTIVE forecasts are Oz Lotto 1709 (17 November) and Powerball 1592 (19 November); 9-12 November is a
  stretch only; if it slips, it slips a week, and the catch-up covers the missed draws (ratified: FB-1).

## 11. Still open (decided in the Mode H design, not here)

Q1 A or B and the final wording; Q4 the prospective deadline; Q5 the install-date rule; Q6 the full report's
cadence; Q7 the display rule after opening; Q8 that the weekly session is R3's FINAL mode and "developed" is
its opening; Q9 two packages; a cross-batch report that reuses frozen records (after WF-1C); the owner's later
simplicity (KISS) review.
