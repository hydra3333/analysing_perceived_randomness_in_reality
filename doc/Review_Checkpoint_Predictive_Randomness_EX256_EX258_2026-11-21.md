## 3. Precise preferred ordinary install + walk-forward + updater + catch-up workflow

**Owner's chronological example:** Dataset is through accepted draw M, and installed older methods have been evaluated as appropriate up to M; their M+1 next forecast may already be frozen. A nominated batch of K new variants has been reviewed and receives **one owner install/release GO**. The logical order requested is:

| Stage | Action | Data/science outcome |
| --- | --- | --- |
| **1. Install = release** | Add K immutable new variant identities, per-variant runnable code and definitions; leave all old variants runnable | The package is the owner's approved released addition; no automatic deactivation, no extra owner activation ceremony |
| **2. Complete historical WF / missing-only fill** | For each eligible already accepted target T from the earliest legal compatible draw through M, calculate ONLY absent `(game, method/variant, target)` canonical predictions/scores, strictly using through T-1; reuse earlier valid score records | Newly added variants attain historical evaluation parity with existing variants; no unnecessary rerun of old versions. Every target's combined research ranking and exploratory OV-1 are recomputed once that target's missing new-variant results are complete |
| **2b. Next M+1 prediction** | Attempt the new variants' forecast for M+1 based only on through-M data, as the logical continuation of WF | A **pending forecast**, not a score: no M+1 outcome is yet in the accepted master. This is NOT automatically a weekly frozen record merely because a development fill ran. The ordinary weekly system must integrate it without overwriting any previously frozen M+1 forecast or changing a previously sealed roster; see §5.3 |
| **3. Results updater** | Retrieve and validate any new official accepted outcomes, extending M through N (N = M is allowed) | The official accepted dataset is now through N; the updater itself does not score or forecast |
| **4. Ordinary catch-up** | Walk accepted missing target M+1 to N, one target at a time, using only accepted earlier draws; all installed eligible old and new variants participate under one agreed frozen per-target roster | Freeze/score each target exactly once, compute the correct per-target prevailing OV-1 factor from eligible participants, update per-draw cumulative rankings and save readable files. If N=M, this stage has **zero accepted targets** |
| **5. Forecast next pending target** | Attempt N+1 for every applicable installed variant using accepted draws through N, unless the exact forecast already exists | Record honest result/pending/pre-draw labels; no clock-based suppression or duplicate frozen forecast |

**Important correction to old shorthand:** Standard historical `--fill` currently fills **accepted result targets only**. It does **not by itself** create the future M+1 weekly frozen forecast; this requires the normal next-target forecast path or a narrowly defined reusable call. Do NOT incorrectly claim that historical walk-forward automatically publishes a prospective M+1 record. The owner desires this end state, and the code design must show how to achieve it.

**Another crucial boundary:** The newly installed versions should not recalculate prior prevailing OV-1 factors for target <= M just because their historical reports now include them. The newly generated historical scores can and should affect the current **exploratory** OV-1 history, but not the previously frozen prevailing stream.

**Normal catch-up is not the scraper:** The updater obtains newly accepted actuals; catch-up processes their missing forecasting/scoring work and then reaches N+1. The user is content if a long historical backfill misses a real pre-draw publication opportunity, but wants the software to attempt every next unaccepted target forecast, not suppress by derived-clock guesswork. If a physical draw has already happened before the actual is ingested, the stored forecast may have a late/operational label rather than a proven pre-event label.

## 4. Statistical and lifecycle subtleties that must be designed, not hand-waved

### 4.1 Active variant versus first eligible forward draw

The owner says **INSTALLATION IS RELEASE**: a single authorisation to add the variant and immediately do its required full historical work. This does **not logically require** a future OV-1 factor to include a participant that had no applicable immutable forecast or was absent from an already frozen weekly cohort. The *first forward-eligible draw number* must be determined and recorded automatically under a reviewed rule without any SECOND OWNER RELEASE CEREMONY.

Propose a minimal algorithm to reconcile:
1. installation/release happens once;
2. historical computation is not held hostage by an unneeded second status;
3. the subsequent ordinary weekly roster includes all newly installed applicable variants as soon as a legitimate new target can be frozen;
4. historical backlog is not silently reclassified as pre-release or retrospectively made prevailing;
5. already frozen weekly sets, historical factors and canonical score keys are not rewritten.

If an M+1 weekly forecast was already frozen for the existing cohort **before** the new package installed, one cannot add the new variant to that old frozen set just by declaring `install=release`. Its independent historical M+1 forecast remains scientific research (or a separately labelled late computation), while the first ordinary forward OV-1 participation may have to wait for the next UNFROZEN weekly target. This is the most important concrete integration issue for Claude to show with a short worked draw-number example. No assumption that the clock can prove physical pre-draw timing.

Likewise, if M+1 becomes accepted while the new variant's historical backfill runs, the project's ordinary target-by-target weekly processing and OV-1 rules must choose an honest cohort using target-independent decisions. Delay of historical processing alone does not make its N-1 research invalid. No special registration, automatic `QUALIFIED` penalty or wall-clock deadline is justified merely by delay.

### 4.2 Target-outcome non-anticipation for new or evolutionary variants

For each target T, the method's forecast, internal adaptation, training features, prior score feedback, possible roster choices and e-factor must depend only on the allowed information before T (or independent randomness), not on its actual outcome. A future evolutionary method may depend on its own historical scores/rankings, but only those for **targets < T**. Historical recalculation of all scores through M and then using the resulting full-M statistics to change a forecast for target T<=M is data leakage, unless clearly labelled exploratory or permitted with a different inference statement. Human evaluation of full backtest results may guide new variant design for future draws; it must not be represented as historical prospective discovery.

The 2.5% anytime error bound is CONDITIONAL on the fair-draw null and correct non-anticipating decisions, not proven by four software integrity checks. Existing numerical OV-1 formula (six e-mixture components, threshold 40, separate games) is unchanged. Python versions are not pinned per historical draw; existing W-23 upgrade review and numerical regression evidence remain.

## 3. The three different operations — owner-understood model, verified design intent

| Operation | Purpose | Relationship to walk-forward | Output |
| --- | --- | --- | --- |
| Results updater | Retrieves, validates and records newly accepted **official** draws | Does **not** itself forecast; must be the reviewed Lotterywest-GOV production source | Updated master/result provenance |
| Historical development walk-forward / **routine fill** | For each missing eligible method/target, calculate using strictly draws `< N`, score against N; reuse existing canonical scores | Ordinary sequential N−1 research over earlier draws | Canonical development history and, once admitted, updated rankings; **exploratory** retrospective OV-1 report/reconstruction |
| Weekly chronological **catch-up** | For accepted draws whose normal weekly processing is incomplete, proceed target-by-target in draw order, strictly N−1; score and record the applicable prevailing OV-1 factor | **Scientifically it IS a walk-forward**, but in a different operational tier, using the roster and records appropriate to each target | Weekly forecast/score/OV-1 records; next-draw forecast as the final step; ranked league publication |

**Illustrative example:** Existing weekly completion through draw M. Results updater appends M+1 through N. Catch-up runs target M+1 with history through M, then M+2 with history through M+1, ... target N with history through N−1, and finally forecasts **N+1** using history through N. Publish scores/rankings and append legitimate prevailing OV-1 factors along the way. If no accepted draw is pending, catch-up has **zero scored draws**, followed by a next-draw forecast if missing. These are conceptually the same N−1 computations as research historical walk-forward; record provenance/evidential classes differ. Do **not** conflate results acquisition with catch-up.

**Existing staged implementation detail:** `Weekly_Session_Orchestrator.py` runs `next`/`score`/`OV-1 record` for each unfinished target, then **publishes a league table only at the end of the session**. Thus a single weekly draw yields a stored table, but multiple catch-up draws currently yield one end-of-session table. The original draft retains clock-based gating for next forecast and OV-1, now in conflict with the user's latest direction (see §5).

**Existing staged routine fill:** MHUP-B design supplement §7.1A explicitly says only **missing method/target pairs** are run, reusing existing canonical scores. Staged `Run_Development_Batch.bat --game G --fill` implements a planner which reports `NOTHING_TO_FILL` where all eligible pairs are covered, otherwise runs, reports, admits and publishes. This is preferred over recomputing every already successful method. However, it currently requires released/runnable method identities; the installed older `WF_BATCH_PLAN_V1` uses an all-cohort plan for its own historical window. The `--variants` option in the staged sequencer belongs to exploratory `--rerun`, NOT the normal missing-results `--fill` operation.

**Crucial overlap issue for redesign:** If routine fill calculates some targets M+1..N before the weekly workflow has processed them, it must not create a second canonical score or pre-empt normal weekly freezing. Design §7.2 says routine fill beyond the holdout can fill already **closed** weekly targets, not weekly targets still open. Thus the simplest desired implementation is fill gaps in already-closed historical targets, then let weekly catch-up handle the open interval using the complete new and old roster. Distinguish historical backfill and ordinary weekly catch-up to avoid duplicating scores.

## 4. Method / family / variant / revision: inspected facts

- The project registers permanent scientific **`method_id` E_n** for each scientific hypothesis. **Every method belongs to its own E-number identity** whether it has one variant or many; a method with one variant is perfectly normal. Not every catalogue E-method is implemented yet.
- A **variant** is a separately named estimator, fit, window, data view or other alternative under the same E-method hypothesis. The stable scientific identifier includes `(game_id, method_id, variant_id, method_revision)` in records. The original method version is often variant ID ending `_V1`.
- A **revision** presently means a new approved, immutable behaviourally relevant implementation/specification of an existing variant. Its code can overwrite the former active implementation and archival code becomes non-runnable. Current registry has one `active_entry` for each `(game, method, variant)` chain; changing same-variant revision automatically disables the older revision's ordinary dispatch. **This conflicts with the owner's keep-all-running policy.**
- **Physical layout:** the actual source tree has one directory per implemented E-method (`src/methods/E_003/`, `E_004/`, `E_006/` ...). A method with a SINGLE variant uses the same E-directory pattern as one with several. **There is currently NO guaranteed individual source subfolder for every variant.** `E_003/` contains `contract.py` plus `variants.py` with SIX variants in one table; it shares mathematical helpers with E_004. The directory belongs to the E-method, not necessarily each variant. Some methods have atypical legacy layouts (E_001 also has a historical wrapper); do not assume completely uniform physical organisation.
- **Current possible future design:** use a NEW VARIANT ID for each behaviourally different replacement/extension so it coexists under the current registry. A method with a single variant remains a one-member family. `method_revision` remains a useful immutable code/contract identity for fixes and technical traceability, even if new *scientific behaviour* is normally represented as a distinct variant; its formal semantics are NOT yet revised/ratified.
- **Shared code caution:** if changing a shared helper modifies old variant behaviour, the old scientific implementation must not silently change. Proposed options include stable/versioned helpers or embedding a variant-specific copy of behaviourally changing logic. Do not require duplicated code where the shared contract is genuinely immutable. The owner has asked to discuss whether ALL variants (including singleton families) should use a consistent per-variant subfolder. This is **NEW discussion, not yet approved**. A large rewrite of existing code/imports/registry paths needs a proportional benefit and independent tests; an approved regular naming/layout convention for future additions may suffice.
- The word **family** is ambiguous in some older specifications (e.g. output schema families). In this discussion use **E-method/hypothesis = family**, **variant = family member**, and do not renumber an existing E-method when merely adding a new alternative under the same scientific hypothesis without owner decision.
