## 1. Numerical quality: wide types throughout [OWNER-DECIDED]

- **Do not squeeze numeric storage to save memory.** The common development table stores each numeric draw-number, main-ball, supplementary-ball and Powerball field using **NumPy `int64`**; any floating numeric columns use **NumPy `float64`**. This also applies to every integer/float array delivered in every scientific `DrawView` (`UNORDERED_SET`, `OPERATOR_DRAWN_ORDER`, `PAIRED_DIAGNOSTIC`). Do **not** use `int8`, `int16`, `int32` or `float32` internally for these numeric fields merely as a space optimisation. Dates remain explicitly typed ISO date / `datetime64[D]` rather than fictitious floating or timestamp fields. Plain Python lists return ordinary Python `int` values.
- **C1 N−1 isolation remains independent of dtype.** Each scientific view array is a new, read-only **byte-backed owned copy containing *only* its permitted training prefix**, converted to `int64`/`float64` *when constructing* the view. Verify for each numeric array that `arr.base` is a `bytes` object and its exact length is `count × row_itemsize` (with the appropriate column factor); no attribute or base chain can reach target-or-later rows. Never return a slice retaining a larger master as `.base`.
- **Required numerical dtype tests:** every integral view array reports `dtype == numpy.int64`, and every floating array (if present) reports `dtype == numpy.float64`. On a scientific view, an integer calculation `47 * 47` must yield **2209**, not fixed-width wraparound. Test the same for all three view types, including paired fields. Python-list accessors return true Python integers. Do not hash NumPy binary buffers/dtypes: training-view digests serialize the approved canonical Python-number representation.
- **Limits still exist:** `int64` is exact only within its signed 64-bit range (up to 2^63−1); potentially larger counts, factorials, combination counts and exact probability numerators must use Python arbitrary-precision `int` or an explicitly justified exact representation. `float64` ordinarily offers ~15–17 significant decimal digits, *not* arbitrary accuracy. For very small probabilities, use numerically stable formulations (for example log-domain calculations), and where justified compare with higher-precision reference arithmetic (`decimal`, `mpmath` or a verified equivalent). Check rounding, overflow, underflow, finite outputs, conditioning, normalisation and convergence method by method.
- **E_1 compatibility is non-negotiable:** the legacy `E1_REAL_U_TRAINING_VIEW_V1` encoding, training digest `d47fbbd6...4339` and accepted draw-1577 canonical result `7f113087...164e` must remain unchanged. A new `DrawView` dtype is **not** a reason to modify canonical digest bytes. Target 1577 is a **forecast-only** regression from draws 1144–1576; never parse its outcome or score it.

## 2. Dependency management and freezes [OWNER-DECIDED]

- `install_upgrade_dependencies_into_venv.bat` **defaults to installing and upgrading** dependencies, as specifically requested by the owner to benefit from bug fixes and current numerical correctness. Do not silently change that default to verification-only. Record before/after package versions (`pip freeze`), Python/NumPy/SciPy and numerical-backend versions, and environment provenance.
- **After *every* dependency upgrade**, run the applicable complete offline test suites, mathematical boundary/precision checks, and the frozen Powerball E_1 draw-1577 forecast-only view/result goldens **before any subsequent scientific work**. A failing regression is a STOP pending investigation, not permission to silently regenerate golden expectations.
- **No dependency upgrade between a forecast's freeze and its scoring.** The forecast/scoring evidence binds its environment; do not swap dependencies mid-observation. **No dependency upgrade during a Mode H holdout study.** Its frozen study manifest must pin the environment as required by **R3-T50**; an environment change requires a separately reviewed study protocol rather than an in-place upgrade.
- Newest packages are *not automatically numerically superior in every algorithm*. Preserve regression and version evidence; confirm behaviour empirically.

## 3. Training, retraining and cache correctness [OWNER-DECIDED]

- **For every forecast target N, fit afresh using only eligible known draws with `draw_number < N`**, subject to the method's predeclared scientific history/window rules. In an ordinary prospective forecast, that normally means all latest eligible pre-target draws. Historical walk-forward recomputes a separate fit for each target's N−1 prefix. Never fit a past target with later rows from the present master; master hash is provenance, not seed/fit/readout data.
- **Incremental fitting or cached intermediate states are optional future optimisations, not the default.** Such an optimisation must be demonstrated by a reviewed regression test to reproduce the **from-scratch fit byte-identically** for the same approved input, method, variant and environment before use. If byte identity is technically unachievable, do not silently reduce this requirement; propose a specific, separately reviewed contract change with numerical equivalence criteria for owner decision.
- Retain frozen forecast, method/configuration, canonical permitted-view digest, master version/hash, runtime/dependency identities, fit/readout identity and post-outcome score records. Retain intermediate fit arrays/checkpoints **only where method-specific reproducibility, stochastic evidence or recomputation cost requires them**. There is no blanket requirement to archive every intermediate iteration.
- **No new Mode H, FINAL or score access.** First quarantine begins Powerball 1577 and Oz Lotto 1694; their outcomes remain excluded from development. E_1 target 1577 regression is forecast-only. Mode H requires a future independently reviewed freeze-before-outcome protocol.

## 4. Implementation and review acceptance

- Numerical-storage type checks and no-truncation tests must exercise both the master table and returned byte-owned views, including paired views. Inspect all numerical columns, not just ball labels.
- Prefix-poisoning, hash/ledger-pinning, symlink/hardlink rejection and method isolation tests under Claude C1/C2 remain required **before scientific use**; passing dtype checks alone is not sufficient.
- Rerun offline suites and E_1 goldens after each dependency upgrade. Test scratch-refit versus any new cache, and archive the exact test and dependency evidence. Reviewed algorithm-specific numerical tolerances still apply where relevant.
